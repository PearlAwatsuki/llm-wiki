# アウトフィット（装備品）

フェーズ6 設計時（2026-06-12）にユーザーが言語化したルール解釈の記録。
outfitBase 共通フィールドの意味と UI 設計の根拠を定める。一次情報はユーザー。
分類・部位行・解説参照の記述は2026-10-09の現行実装に更新。

## 共通パラメータ

### buy — 購入値（略号「購」）

- 購入判定の目標値。購入判定は基本的に「★信用」技能で行う
- 本来は常備化経験点（preserveExp）と合わせて一つのパラメータであり、
  「購：購入値／常備化経験点」の形で表記する
- 値は「なし」「数値」「解説参照」の 3 状態（UI はドロップダウン選択）
  - なし → 「-」表示
  - 数値 → その数値
  - 解説参照 → preserveExp の表示を消し、「購：解説参照」とだけ表記する
- DataModel 表現: `buy: { mode: none/value/reference, value: Number }`

### preserveExp — 常備化経験点

- 常備化（プレアクト時点までの購入）に必要な経験点
- 「なし / 数値 / 解説参照」の3状態。値のない場合は「-」、解説参照は「解説参照」と表示
- DataModel 表現: `preserveExp: { mode: none/value/reference, value: Number }`

### hide — 隠匿値（略号「隠」）

- アウトフィットを発見するための〈知覚〉判定の目標値
- 危険値と合わせて「隠：隠匿値／危険値」の形で表記する
- 値は「なし」「数値」「解説参照」「制御値」。制御値は `control` で保存
- **解説参照でも危険値は別個に設定・表示される**（例: 「隠：解説参照／-1」）
- DataModel 表現: `hide: { mode: none/value/reference/control, value: Number }`
- `system.isDisguisedHide`（Boolean、既定 false）: 一見無害なものへの偽装。隠匿値の下の「偽装」チェックで設定し、数値表示を `（20）` のように括弧で囲む。隠匿値の数値計算は変更しない。

### appearancePenalty — 危険値

- 携帯していると、全アウトフィットの危険値の合計分が登場判定目標値への修正になる
- 「なし / 数値 / 解説参照」の3状態。値のない場合は「-」、解説参照は「解説参照」と表示
- DataModel 表現: `appearancePenalty: { mode: none/value/reference, value: Number }`

### hack — 電脳制御値（略号「電制」）

- アウトフィットへのハッキングを試みる〈電脳〉判定の目標値
- 「なし / 数値 / 解説参照」の3状態
- シート表記は略号「電制」を使う（2026-06-12 確認）
- UI は購入値と同様のドロップダウン選択（なし/数値/解説参照）
- DataModel 表現: `hack: { mode: none/value/reference, value: Number }`

### part — 装備部位

- 一つの部位には基本的に一つのアウトフィットしか装備できない
- 二つ装備可能な部位: 「片手持ち」「片腕」「片足」「指」の 4 つ
  - 「両手持ち」=「片手持ち」×2、「両腕」=「片腕」×2、「両足」=「片足」×2 を消費
- 「籠手」は手系の装備部位（「片手甲」「手の甲」「指」等）を全て埋める排他関係
  （「片手持ち」など“持つ”系は例外）
- 「武器2」のように後置数字が付く場合、その部位のスロットをその数だけ消費する
  （「武器2」は武器スロット 2 つ消費 → スロットが 2 つ以上ある場合のみ装備可）
- 種類が多すぎるため **部位名の UI は自由入力**（ドロップダウンにしない）
- 部位名とスロット数は別フィールドで設定する（2026-06-12 確認）。
  表記はスロット数 1 のとき部位名のみ、0 または 2 以上のとき「武器2」「部位0」のように数値を付す
- **複数部位を占有する場合がある**ため行の追加・削除に対応（2026-06-13 確認）。複数行の連結表記は下記「部位管理」の表示ルールへ移行（2026-06-26）

#### 部位管理（2026-10-09 更新）

部位は**ユーザー入力ベースで管理**する（特定部位を持たないキャラ等、部位ルールが多く自動入力に任せきれないため）。公式の「部位」指定（任意系・複数部位・表記ゆれ含む）をすべて、自由入力の値＋数個のフラグで表現する。

##### part 行のスキーマ

各 part 行は **5択の種別（kind）** を起点に、種別連動の入力を持つ。

| kind | 入力・意味 |
|---|---|
| `none`（「-」） | 部位なし（非消費） |
| `bodyPart`（身体部位） | プリセット由来の部位名（`value`）＋消費数（`slots`） |
| `option`（オプション） | ホストを `hostMajor` / `hostMinor` / `hostMinorExclude` / `hostFeature` / `hostKey` で指定し、`slots` で消費数を保存。`hostKey` はアイテム名ではなく識別キー。分類は主分類・副分類を合わせて照合する |
| `reference`（解説参照） | 表示は**常に「解説参照」**（説明タブはルルブ表示を完全踏襲）。下に部位設定欄（`bodyPart`／`option`／`other`／`none`。**解説参照の入れ子は不可**）を持ち、**占有計算には実部位が効く** |
| `other`（その他） | 自由記入（`value`）。占有計算対象外 |

- **任意は各行の `optional`**。チェックした行は占有数にカウントしない。他行の必須／選択候補とは独立。旧行の未設定値（null）は `partOptional` を参照するが、明示的な false は旧全体フラグより優先する。
- **各行の `requirement`**: `and`＝「必須」、`or`＝「選択候補」。必須行をすべて占有し、選択候補から `partOrChoice` で選んだ1行を占有する。選択が無効なら最初の候補を使う。旧行の未設定値は `partRelation` を参照する。
- 旧 `isOption` フラグ・旧 part 種別（slot/outfitName）・restrictCategory は**この5択＋ホスト指定**に吸収（廃止。アウトフィットシートの「性質」→「特性」改名・旧オプションチェック/装備対象は撤去）。
- **既存 part データ（`{value, slots}`）は kind=`other`（自由記入）へ移行**（§4.2＝文字列から種別を推測しない／表示は保たれる）。
- DataModel 表現: `part: ArrayField({ rowId, kind, requirement, optional, value, partKey, slots, hostMajor, hostMinor, hostMinorExclude, hostFeature, hostKey, refSubKind })`。`rowId` は行の安定ID、`partKey` は身体部位の参照キー。兄弟の `partOrChoice` は行番号、`partRelation` / `partOptional` は旧データ互換用。
  - **`hostKey`（2026-07-23 改名・旧 `hostName`）**: 名前指定ホストの**識別キー参照**。自由記入を廃し、アウトフィット辞典（`packs/outfits`＋`works-outfits`）から**上位のホスト記述子（大分類/小分類/除外/特徴）で絞ったプルダウン**で選ぶ。保存＝識別キー、表示＝逆引きした現在名（`identification.mjs`・保持名キャッシュなし）。ホスト記述子を変えると `hostKey` はリセット。**旧データは考慮しない**（ユーザー確定）。

##### 表示ルール（ルルブ表記に一致させる・実装は純粋関数 `part-helpers.mjs`）

- **身体部位は数字を付けない**（「片手持ち2」とはしない。2占有は専用部位名＝両手持ち がある）。数字は占有計算と**オプション専用**（武器0 等）。
- 必須行は「+」で結合する。選択候補は全体2行なら身体部位「A、もしくはB」、option「A／B」。全体3行以上なら「AかBかC」。混在例は「生身+片腕か片脚」。
- 一部の行が任意なら、同じ結合内の任意行を一括して括弧で囲む。例: 「生身+任意(片腕か片脚)」「生身+任意(片腕+片脚)」。**全行が任意なら従来どおり「任意(A、B…)」**（読点区切り）。`other` を含めば内側末尾に「など」、値がなければ「任意」。
  - 例: 全行を任意にした〔other・option武器・option防具〕→ **「任意(武器、防具など)」**
- **正本＝ユーザー提供の「部位名表示リスト」**（2026-06-27 再送。最初に渡されたものが正式表記）。表示は逐条この正本に照合し、**ルールから単純導出できない例外を取りこぼさない**こと。
- **オプションの部位名（スロット名）**: アイテム名あり→名前（アサルトナーヴス）。なし→スロット名。
  - **大分類レベルでスロットを共有する大分類は大分類名**（小分類/特徴は括弧で絞る）。これは**スロット持ち型から逆算**（`isMajorLevelSlotMajor`）するが、ルルブは経験的に**武器のみ**該当＝`MAJOR_LEVEL_SLOT_MAJORS=["weapon"]`。武器／武器(白兵武器)／武器(射撃武器)／武器0(白兵武器)／武器(搭載兵器以外)／武器(搭載兵器)／武器(レーザー武器)／**武器(サイバーウェア)**（`isCyber` 由来。実装 TODO）。
  - 大分類の絞り特徴は `hostFeature`（`PART_HOST_FEATURE_LABELS`）: `isLaser`→「レーザー武器」、`isCyber`→「サイバーウェア」（**武器(サイバーウェア)**。2026-06-27 ユーザー確定＝サイバーウェアは絞り込みに追加するしかない）。
  - **例外は特殊弾のみ**（2026-06-27 ユーザー確定）。`specialAmmo` は大分類「武器」に畳まず **「特殊弾」**。装着先の武器名（ホスト名）があれば **「特殊弾(スリング)」**＝**「種別(ホスト名)」**形式。**他の小分類はルール通り**で例外はこれだけ。
  - **それ以外は小分類名**（船舶・タップ・IANUS）。ヴィークルは構造同型でも小分類名（武器が例外。理由不明・ユーザー観測 2026-06-26）。
  - **タップのソフト/ハードはルール上の部位表示は「タップ」だけ**（部位名では soft/hard を区別しない）。software/hardware 小分類は `SLOT_KIND_MINOR_HOSTS` で「タップ」へ置換（**正式表記は最初に渡された部位リスト**が正本）。
  - **意識系（表層意識/深層意識/無意識）はそのまま表示**（IANUS には畳まない）。IANUS のオプションは「IANUS」。**意識系は「IANUS を装備して解放される身体部位」とも見なせる**（精神という部位の存在から）。
- 実装: `formatPartDesignation`／`formatOptionLabel`／`computePartOccupancy`／`computeHostOccupancy`／`joinPartDesignations`（Foundry 非依存・part-helpers 39 テスト）。

##### キャスト部位スロット集合・占有

- **キャストが「部位スロット」の集合を持つ**（`partSlots = [{key, value, count, occupiesOther, targetPart, targetKey, targetCount}]`）。ゲーム設定で**全アクター共通の初期プリセット**を定義し、新規キャストへ流し込む。キャスト側でも追加／削除できる。プリセットはフェーズ10で設定まで完了。プリセット編集 UI はカード設定アプリ様式（standard-form・number-input-spinner）。
- **部位キー（フェーズ12）**: 各部位スロットは `key`（安定参照）と `value`（表示ラベル）を持つ。**AE（`system.partSlot.<キー>`／アイテム part 行の `partKey`）・エイリアス（`targetKey`）・負傷の `partSlotMod.part` の参照はすべてキー**で持ち、表示は**逆引きした現在ラベル**（ラベルのリネームで参照が壊れない＝識別キー・分類コードキーと同原則）。既定ラベルは英語キー（`one-hand`＝片手持ち・`occiput`＝後頭部・「〜部」は `-part` 等・2026-07-15 ユーザー確定）。既存ワールドは ready の `migratePartSlotKeys`（GM・**スキーマ版 `partSlotKeyScheme` でゲート**）が既定ラベル行を既定英語キーへ揃える（プリセット＋全アクター・カスタムラベルはキー尊重/無ければ生成）。**版番号ゲートなので、キー命名を変えて版を上げれば付与済みワールドにも波及する**（旧ローマ字キーからの差し替えも次回リロードで自己修復＝手作業不要。旧 boolean フラグ方式では再移行できなかった）。占有照合は**キー優先・ラベル後方互換**（辞典・既存 part 行はラベルのみでも当たる）。設定アプリはキー列を追加しウィンドウ幅を拡張。
- **AEによる部位の増減・追加**: 通常AEの `system.bodySlot.<キー>.capacity` で身体部位容量を変更する。付与AEの `system.equip.required.<キー>` / `system.equip.alternative.<キー>` で必須／代替部位を追加する。値は0以上の整数となる式。個別行の追加・変更・削除は `system.equip.rows` を使用する。`system.equip.parts` は旧形式の配列追加／全体置換。[Active_Effects.md](../Game_Mechanics/Active_Effects.md) を参照。
- **「指定部位を複数占有」エイリアス**（`occupiesOther`）: ある部位スロットを「別の指定部位（`targetPart`）を `targetCount` だけ占有する」エイリアスにできる。**両手持ち＝片手持ち×2** 等をこれで表現（占有時、両手持ちは片手持ちを2消費・count は無視）。公式に無い**排他部位**やルール追加にもユーザー設定で対応できる。占有計算はエイリアスを実部位へ展開して数える。
- **プリセットは体部位のみ**。個数は **片手持ち／片腕／片脚／指＝各2**、その他は各1。**両手持ち＝片手持ち2** 等は atomic（`{片手持ち, slots:2}`）で表現。**完全一致照合**（耳≠両耳、腕部≠腕 は別部位）。`下垂体` は `脳下垂体` を正としプリセット不採用（`任意(下垂体)` は非カウントなので衝突しない）。
- **並び順の原則**（2026-06-29 ユーザー確定）: 頭→足→全身/組織→内的→スコープ。**装着物は装着先の身体部位群の末尾**に置く（靴=脚末尾・ヘルメット等=頭末尾）。**装着先が不定の装着物**（衣類・携帯・装飾・外付けの護符/結界/操縦）は**全身の近く**にまとめる。電脳・精神・魂・血統は**内的（心・霊）**として全身組織の後、各部・独立は**最も非局所**として末尾に置く。
- **占有 = 準備済みアウトフィットの part を部位ラベルごとに合算**し、キャストの該当スロット count と突き合わせる。
- **スロット非消費は3パターン**で母数から外す: ① `slots===0`（武器0 等）／② 小分類が**住宅アクセサリ**／③ **該当行が任意（optional）**。
- **オプションの占有はホスト（`parentItemId`）のスロットから導出**（`computeHostOccupancy`。装備先 UI は部位カード最下段の `parentItemId`/`parentSlotKind`）。占有チップのスロット名は、**意識3種・soft/hard はその種別名のみ**（表層意識／ソフトウェア。「IANUS/表層意識」「タップ/ソフトウェア」にはしない）、`normal` はホストのカテゴリ名（武器/IANUS/船舶/タップ）、**便宜スロット `outfitName` はホスト名**（＝アイテムごとに変わる。種別ラベル「アイテム名」は内部キー用で、表示には出さない・2026-07-23 是正）。
  - **ホスト名は同名スロットが複数あるときだけ括弧併記**して区別する（**IANUS は単一準備で常に一意＝`IANUS(IANUS)` を出さない**。2026-06-27 ユーザー確定）。括弧は半角。
  - **スロット0／無スロットは実スロットとしては拾わない**（容量>0 の実スロットのみ 0/容量 を出す。2026-06-27 ユーザー確定）。**ただし** スロットなしホストは**便宜スロット「アイテム名」を1つ持つ扱い**（下記・2026-07-23）。
  - **便宜スロット「アイテム名」（`outfitName`・2026-07-23 ユーザー確定）**: スロットを持たないホストへ**名前指定で装備する**オプション用に「アイテム名スロットが1つある」扱いにする仮想スロット（容量1）。`computeHostOccupancy` が容量1で扱い、**2個目は超過＝「対象1つにつき1個だけ準備可能」の制限が占有計算で自動的に効く**（別レイヤの準備数制御を作らない）。表示は**占有が発生したホストにだけ** 親アイテム行のゲージで 1/1 を出す（全スロットなし品に 0/1 は出さない）。便宜スロットのスロット名を出す箇所（占有チップ・装備先ドロップダウン）は**ホスト名**（種別ラベル「アイテム名」は内部キー用で表示しない）。ホストの `slots[]` には保存されず、オプション側 `parentSlotKind=outfitName` としてのみ現れる（`SLOT_KINDS.outfitName`）。装備先が**スロットなしなら `parentSlotKind` を既定で `outfitName` に自動設定**。
- **空き/埋まり・超過は表示のみ**（秘技/奥義の取得数表示と同思想）。自動強制・notification はしない。**超過時はシート上で視覚強調（赤等）**。
- §4.1: 部位ラベル集合の同梱は**構造的最小限**（短い機能ラベルの語彙集＝enum 相当）として許容。ラベルのみに留め、解説文・対応表は付けない。プリセットの中身（体部位ラベル・個数）はルール由来のためユーザーが editor で完成させる。

##### UI（D&D 5e「消費(Consumption)」UI を参考・2026-06-26）

- アウトフィットシートの部位設定は独立fieldset。行追加ボタンと、各行に「必須／選択候補」および「任意」チェックを置く。全体の結合・任意トグルは使わない。
- **行＝ブロックカード**（D&D の消費ターゲット カード様式）。上段に **種別(kind)｜消費数(slots・? ツールチップ)**、下段に**対象欄**を種別連動で表示。右下に削除。
  - 身体部位→部位、オプション→大分類/小分類＋除外/その他特徴/アイテム名、その他→自由記入、解説参照→入れ子(身体部位/オプション/その他)＋ラベルは常に「解説参照」、`-`→対象欄なし。任意チェックと消費数は `-` 以外で表示。
- **対象欄は文脈連動**（D&D の「目標」流）:
  - **ワールド直下**（辞典・ディレクトリ）＝身体部位はプリセット＋（その他）自由入力。
  - **キャラクター所属**＝身体部位は**キャストの partSlots ラベル**からドロップダウン。
  - **オプションのアイテム名（`hostKey`）は直下・辞典・アクターいずれも**アウトフィット辞典のプルダウン**（上位のホスト記述子で絞る・2026-07-23）。旧「アクター所属時のみ所有アウトフィット名」から辞典参照へ統一。

##### ホスト指定の統合（二本立て解消・2026-07-23 ユーザー確定）

旧来はホスト指定が二本立てだった: ①部位行の記述子（`hostMajor`/…/`hostName`）＝ラベル＋アイテム名絞りで**大分類跨ぎ可**、②トップレベル `parentItemId`/`parentSlotKind`＝占有/入れ子/AE転送/`@item.parent` の実バインドで**自身の大分類で絞り＝跨ぎ不可**。同じホストを2箇所に二重入力する構造で、搭載兵器（武器）→ヴィークル のような**別大分類ホスト**を装備先に選べなかった。

- **統合後**: 実バインドは `parentItemId`（＋`parentSlotKind`）**一本**。部位行の記述子は「定義上のターゲット指定（何に付くか）」に純化し、**装備先候補の絞り込み**と**素のラベル**を駆動する。装備先候補は共有純関数 **`matchesHostDescriptor(host, spec)`**（`part-helpers.mjs`）で絞る＝アイテム名辞典と**同一判定**。`hostKey` があれば識別キー一致の所有品、無ければ種別一致。**自身の大分類では絞らない**＝別大分類ホストが通る。
- ラベルの具体ホスト名は `hostKey` を **live 解決**（`resolvePartRowsForDisplay` が現在名を行へ注入→`formatOptionLabel` が読む。「特殊弾(スリング)」「アサルトナーヴス0」等）。未指定/未解決は種別ラベル。
- 占有・入れ子・AE転送・`@item.parent` は無改修で `parentItemId` を見るため整合。IANUSオプション（general／ホストは ianus 型＝別 Item type だが同大分類 cyberware）も本統合で自然に扱える（別**大分類**の代表例が搭載兵器）。
- **入れ子行の列は移動先の表に合わせる**（2026-07-23 是正）: 準備で別大分類ホスト配下へ入れ子表示されるオプション（搭載兵器→ヴィークル 等）は、行の列値を**元の大分類の列でなく装備先グループの列**で計算する（`_prepareOutfitRow` は実効準備済みの入れ子オプションのとき `parentItemId` のグループを使う）。ヴィークル表の「攻」に搭載兵器の攻撃力が入り、ヴィークル固有列（SF/乗員/ス等）は「-」。装備先の表に無い元カテゴリ列（射等）は出さない。
- **入れ子行のスロット名タグとゲージのツールチップは廃止**（2026-07-23 ユーザー確定）: ホスト側スロットには本来の名前が無く、分類名（「地上車両」等）や便宜スロットのホスト名を「スロット名」として並べる見せ方が破綻するため。どのスロットに載るかは**入れ子（ホスト直下）で自明**。**親アイテム行の容量ゲージ（残容量・超過=赤）は残す**（そのホスト自身の行なので名前不要・ツールチップも無し）。占有パネルのホストスロット占有チップ（分類名／便宜=ホスト名）は従来どおり残す。
  - アイテム名は **`hostKey` の識別キーから現在名を逆引き**する（名前やUUIDを参照キーとして保存しない）。
- 選択候補の装備先はItem Sheetの `partOrChoice` で指定する。占有側だけに影響し、説明タブの候補表記は変えない。

- 特定のスタイルやオーガニゼーション専用であることを表す

### 真偽値フラグ（意味は 2026-06-12 ユーザー確定）

| フラグ | 意味 |
|---|---|
| `isPrepared` | **準備済み**。そのアウトフィットが使用可能な状態にあるかどうか。いわゆる「装備」に近い概念だが、大きさや機能的に身に付けられないアウトフィットにも適用される点が異なる |
| `isCarrying` | **携帯中**。そのアウトフィットを身に着けているかどうか。「所持」しているだけでは携帯中とはいえず、当然準備中ともいえない。キャラクターシートに存在する時点で「所持」は確定しているので所持フラグは存在しない |
| `isCyber` | サイバーウェアかどうか。種別がサイバーウェア以外のアウトフィットでサイバーウェアであるものを識別するのに必要 |
| `isPre-play` | **プレアクト購入**。常備化経験点は支払っていないが、プレアクトで購入して所持しているアイテムであることを表す。true だと所持した際の経験点消費がなくなる（表示名は TNX 用語の「プレアクト購入」とする。2026-06-13 確定） |
| `isOption` | そのアウトフィットが**別のアウトフィットに装備するオプション**であることを表す。装備対象のアウトフィットのスロット数がなければ装備できない（2026-06-12 確認）。**オプションは装備先（親）が準備済みでなければ準備できない**（下記「オプションの準備ゲート」・2026-07-23） |
| `isMutantOrgan` | **変異器官**（ヒルコの自製生体装備等）。部位オプションの「その他特徴」ホスト条件で対象を絞るのに使う（2026-06-29 追加） |
| `isShiki`＋`shikiType` | **式神装備**（しきそうび）。true のとき**タイプ**（`shikiType`＝攻撃/防御/操縦/独立）を持つ。説明タブではタイプを「部位」の1つ前に表示（2026-06-29 追加） |
| `isDerivedData` | **派生データ（本体）**。別アイテムから派生した従属データ。**常備化経験点を消費しない**（派生元が負担＝二重計上回避）。取得は派生元の自動生成による。設定UI は特性セクション。**`hasDerivedData` ON のアイテムでは非表示**（派生元は自身が派生データでない）（2026-06-29 追加） |
| `hasDerivedData`＋`derivedDataRefs` | **派生元**。派生データ（`derivedDataRefs`＝UUID＋名前の配列）を持つアウトフィット。取得（インポート）時に参照先を全て複製生成し `isDerivedData=true` を付す（選択なし・全自動）。例: Tウェポン→タップ＋武器。UI はスタイル技能の自動取得と同形（ドロップエリア＋参照ボタン＋右クリック閲覧/編集/削除）（2026-06-29 追加） |

- `isCarrying` はフェーズ6 設計時に必要と判明し追加。**デフォルトは true**（2026-06-13 確定）
- 携帯/準備でどのパラメータ・効果が適用されるかは「生身・パラメータの適用宣言・携帯/準備の適用範囲」（2026-07-02）を参照（携帯のみ=危険値の登場判定修正だけ・準備で常時効果/パラメータ/使用が解禁）
- **部位「-」（占有部位なし）のアウトフィットは準備できない**（2026-07-09 ユーザー・ルール反映）。この場合 `noPrepareRequired` を立て（`isPartless` から派生）、**準備トグルを非表示**にし、**未準備でもデータ・効果が適用される**（例外品。既存の `noPrepareRequired` フィールドの本来の用途）。消費側は `isPrepared || noPrepareRequired` に統一（制御値/CS修正・cs.base/ar の AE ゲート・電子妨害の対象集計）。本体 `aeb6d3e`。

## 故障・破壊（isMalfunction / isDestroyed）（2026-07-18 ユーザー確定）

アウトフィットが受ける**使用不可状態**。どちらも真偽値フラグ（`isMalfunction`＝故障・`isDestroyed`＝破壊、initial false）。

- **故障（isMalfunction）**: 対応する〈製作〉での**修理が可能**（→「修理」用途。Usage_System.md）。
- **破壊（isDestroyed）**: 基本的に**アクトが終了するまで直らない**（在ゲームの修理用途では解除できない）。
- **どちらも受けたアウトフィットは使用できない**:
  - そのアウトフィット自身のロール（アイテムロール）ができない。
  - その武器を「使用武器」に持つ攻撃判定もできない（`useAttack` が使用武器の故障/破壊を弾く）。
- **アクト間に持ち越さない**（消費アイテムと同じく次のアクトまで引き継がれない）。**アクト終了時の自動リセット機構は未実装（将来フェーズ）**。現状は手動でオフにする（フラグと付与手段だけ先行実装＝2026-07-18 ユーザー指示）。
- **サービス大分類は免疫**: 大分類 `service` のアウトフィットは故障も破壊もされない（実効フラグを常に false に落とす＝`isOutfitServiceImmune`。アイテムシートでも故障/破壊トグルを出さない）。
- **AE で書き換え可能**: `isMalfunction` / `isDestroyed` を `AE_FLAG_PARAMS` に登録（実効読みは `readFlag`／照合は `isOutfitMalfunctioning` `isOutfitDestroyed` `isOutfitUnusable`＝`helpers.mjs`）。
- **アクターシート表示**: 故障＝アイテム名を**赤＋取消線**、破壊＝**グレーアウト＋取消線**（両方立つと破壊＝グレー優先）。その状態ではロール不可。
- 付与手段: アイテムシートのヘッダートグル（サービスは非表示）／AE。解除は故障のみ「修理」用途（判定成功で `isMalfunction` を false へ）。

### サービス／バックグラウンドの準備固定（2026-07-18 ユーザー確定）

小分類 `background`（大分類サービス配下・グローバル一意）のアウトフィットは**必ず準備・携帯され、未準備にできない**。`isPrepared`／`isCarrying` を派生で常に true に固定し（`isPartless` の「準備できない=オフ」より優先）、**アイテムシート・アクターシート双方で携帯/準備トグルを非表示**にする。

## 消費アイテム（isConsumption / quantity）

2026-06-12 ユーザー確定。weapon の旧 isthrow（投射武器）を全種別に一般化して置き換えた。

- `isConsumption` が true のアイテムは個数（quantity）を持ち、アイテム名の右に「×数字」で表示する
  （この数値入力は number-input-spinner を**使わない**例外）
- 消費で現在個数（value）を減らし、0 になるとそのセッション中は使用不可。セッションが終われば復活する
  - **減らし方（2026-07-19 ユーザー指示）**: 個数は**用途の消費先設定**から消費する（`resource="quantity"`・使用回数/残弾と同じ枠組み）。**自動消費は無い**——実装上も元から `quantity.value` を減らすコードは存在せず（読んでいたのは常備化経験点の計算のみ）、2026-07-19 に消費先として選べるようにした。0 での使用不可は、消費先の**残量不足＝原則ブロック**が担う（チェックを外せば卓裁定で実行可）。負値消費＝補充（常備化個数 max が上限）。
- 常備化経験点は個数分（max 基準）必要で、**消費しても経験点は復活しない**
- DataModel 表現: `quantity: { value: 現在個数, max: 常備化個数 }`（initial 1/1）

## 武器（weapon）固有パラメータ（2026-06-12 確定）

- **attack — 攻撃力（略号「攻」）**: ダメージ種別 + 値で「攻：I+4」のように表記。
  ダメージ種別は **S / P / I / X** の 4 種から**単一選択**（ドロップダウン。2026-06-13 確定）。
  **表記は S/P/I/X そのものが正式**（2026-07-21 ユーザー指摘）——従来ここに書いていた
  「斬撃／貫通／衝撃／装甲無視」は**正式なルール用語ではない** Code の付け足しだったため撤回した。
  UI・記録とも S/P/I/X で表記する。
  「攻撃値」というパラメータ名は存在しない（シートでは「攻撃力」1 行で種別 + 値を扱う）
- **guardValue — 受け値（略号「受」）**: パリィをして判定に失敗した際にダメージから引かれる値
  （パリィは白兵判定で、成功すればその時点でダメージ無効）
- **range — 射程（略号「射」）**: 最低射程(min)は なし/至近/近/中/遠/超遠、最長射程(max)は なし/近/中/遠/超遠
  （最長から「至近」を除く。「なし」「武器」はいずれの選択肢にもない。フェーズ6-4 で min/max 選択肢を分離）。
  最低射程が「なし」のとき射程なし。最低=最長なら単点表記、異なれば「近～超遠」表記
- **isLaser**: レーザー兵器。レーザー兵器からの攻撃を受けない防具があるための識別フラグ
- **isFullAuto + FAValue**: フルオート射撃可能な武器。FAn の n（FAValue）をダメージに加算できる。
  **FA 値の自動加算は廃止**（2026-07-18 ユーザー確定）——用途のダメージボーナス式で
  `@outfit.<識別キー>.FAValueTotal` を手動参照する。
- **ammo — 残弾（射撃武器・搭載兵器）**: 弾数のカウンター。**使用回数とは別の資源**であり、
  1つの武器が両方の制限を同時に持ちうる（2026-07-19 ユーザー裁定）——「武器を使用して攻撃する」で
  減る弾数と、「アウトフィットを使用する」で減る使用回数は**ルール上まったく別の行為**のため。
  形は `uses` と揃える：`{isLimit, max, spent}`（`max`=装弾数・`spent`=撃った数・残弾=`max − spent`）。
  自動給弾の武器は `isLimit=false`（残弾を管理しない）で表す。
  射撃1回ぶんの消費も**リロード（＝残弾への負値消費＝回復）も、すべて用途の消費先設定から**行う
  （自動消費は無い）。
  ※同日に一度「使用回数へ一本化」して ammo を廃止したが、上記の共存を考慮していなかったため撤回・
  再導入した。旧モデル（`mode`/`value`/`current`・null=満タン）には戻していない（専用のクランプ・
  回復ロジックを二重に持つ形だったため）。一本化時に破棄した旧データは復元しない（破棄裁定が有効）。
- **attackArea — 攻撃範囲**: 「-/範囲/範囲（選択）/シーン/シーン（選択）」の 5 択。
  設定時、判定アイテムで武器攻撃の用途を設定するときに範囲を上書きできる（「-」は上書きしない）
- ~~**isBiological**~~: フェーズ6-4 で削除。生体装備はカテゴリ「生体装備」で識別する方針に変更。
  weapon の isBiological は 6-2 で outfitBase へ一般化されたが、6-4 でカテゴリ判定に置き換え除去。
- 概要表記順: **購/隠/攻/受/射/ス/電制/部位**（ス = スロット）

## 防具（armor）・サイバーウェア（cyborg）（2026-06-12 確定）

- **defence — 防御値（略号「防」）**: S/P/I の 3 値を「**防(S／P／I)：5／4／6**」のように並記
  （(S／P／I) の部分を省略してはならない。2026-06-13 確定）
- **controlMod — 制御値修正（略号「制」）**: ヴィークル等で出てくる場合も同じ意味
- 防具の概要表記順: **購/隠/防/制/電制/部位**
- **cyborg（全身義体）**: 概要表記順は **購/隠/防/攻/受/電制/部位**。

## 生身・パラメータの適用宣言・携帯/準備の適用範囲（2026-07-02 確定）

戦闘タブ（フェーズ10-6）設計に伴うルール言語化。ユーザー確定 2026-07-02。

### 生身（すはだ）

- **「生身」は武器アイテム**として表現する（運用上、既にキャスト/アクターへ投入済みの前提）。
- 生身の基本値: **攻撃力 I+0・受け値 0**。
- **生身の防御力も実質的に存在**する（アイテムのデータとしては持たないが）: **S/P/I すべて 0**。

### 全身義体・生身変更装備による生身の変更

- **全身義体**は**準備することで**生身のデータ（攻撃力・受け値・防御力）を**義体のデータで完全に置き換える**。
  **加算ではない**（ルール的に正しい解釈は「生身への加算」ではなく「置き換え」）。
- **生身変更装備**は生身（武器）のデータ——具体的には**攻撃力と受け値**——を変更する装備。
- **複数の生身変更装備・義体を同時に準備していても、適用されるのは一種類のみ**。
- **識別（2026-07-02 確定）**: 生身変更装備は**武器アイテムの特性フラグ**で識別する（§4.3 のフィールド追加
  対象・実装は保留中）。※武器の類似フラグとしてかつて `isBiological`（生体装備）が存在したが
  フェーズ6-4 で「カテゴリ識別に置換」として削除されており、生身変更装備の識別子は存在していない。
  変異器官（`isMutantOrgan`・2026-06-29）は部位ホスト条件用の別概念で、代替ではない。
- **書き換えの意味論（2026-07-02 確定）**: 義体・生身変更装備で変更されたデータは**「生身」として扱われる**。
  これらは全て「生身」のデータを**書き換える**ため、**複数準備していても〈二刀流〉〈黒羽の矢〉等で
  互いを合算参照することはできない**（生身は常に1つ＝書き換え結果がその1つを定義する）。
  ただし**「（変更された）生身」と「白兵武器ひとつ」のような選択（組み合わせ）は当然可能**
  （合算系の技能において、生身は1つの武器として数えられる）。
- **攻撃とパリーの使い分け（2026-07-02 確定）**: **攻撃に使う武器とパリーに使う武器は別々に選べる**
  （攻撃と防御でそれぞれ別の武器・身体部位を使うことは設定上も違和感なく同居する）。
  シート上では便宜的に事前設定するが、**本義は武器の使用も生身変更装備の適用も都度宣言**であるため
  非強制（表示のみ）。UI は戦闘タブの「攻撃で使用」「パリーで使用」プルダウンで行い、**候補は準備済みの
  武器全体＋全身義体**（〈二刀流〉〈黒羽の矢〉等の合算はその技能の判定時に扱うため、ここは「基本として
  選択している武器」の設定・2026-07-02 再確定）。空欄＝未変更の生身が既定。
- **「生身（アウトフィット名）」表記（2026-07-02 確定）**: 全身義体・生身変更装備を選択した場合、
  生身のデータを書き換えていることを示すため**「生身（セイバーセンス）」のように表記**する
  （通常武器はそのままの名前）。

### 武器パラメータの参照宣言

- 生身変更装備に限らず、**複数の武器を準備している場合、どの武器の効果を受ける（攻撃力・受け値などのパラメータを参照する）かを宣言**しておかなければならない。
- 準備さえしていれば、**攻撃はこの武器・パリー（受け値参照）は別の武器**という宣言も可能（参照の分割可）。

### 防具の合算

- 防具は武器と違い、**準備できていれば（部位が重ならなければ）すべてのパラメータが合算されて適用**される。

### 携帯・準備の適用範囲（一般原則）

- **携帯しているだけ**のアウトフィットは、**危険値による登場判定への修正しか適用されない**。
- **準備することで初めて**、常時効果を受ける・パラメータを適用する・使用する、が可能になる。
  （制御値修正・CS 修正等の常時パラメータも準備が条件。※ただし**タップの CS 修正は「ゴースト時は適用しない」フラグ ON のとき携帯起点の例外** → 「タップの CS 修正」節）

### タップの CS 修正（2026-07-02・原作事実の記録）

**CS 修正のパラメータを持つのはタップのみ**（非タップのアウトフィットにパラメータとしての CS 修正は存在しない。2026-07-02 確定）。

1. タップの CS 修正は、そのタップを**準備した際の CS ベースへの修正**である。
2. 解説に**「据え置き型」**と書かれたタップは、原作表記上「**携帯してシーンに登場した際**」に CS ベースへ
   修正を受け、携帯キャラクターが**ゴーストとして登場している場合は無視**される——ただし
   **この「携帯して」の表記は誤表記の可能性があり、正否は裁定保留**（2026-07-02 ユーザー）。
3. 直接登場する場合でも、**タップの不携帯を宣言**すれば CS ベースへの修正は当然受けない
   （データ上は携帯フラグ OFF に相当）。
4. 据え置き型以外にも CS 修正を持つタップが存在する。CS 修正が 0 以外のタップは原作で
   **「CS：（-20）」のように括弧書き**で表記される（「ゴースト登場すれば無視できる」条件付き修正の
   含意と推測される。据え置き型でないタップも同表記）。例外として**『CS：0（+1）』表記のタップが1つ**存在し、
   通常の CS 修正と適用条件が異なる（準備済み＋条件充足で括弧内の値になると思われる）。
5. **他のマイナス修正が主となるデータ（防具・ヴィークルの制御値への修正など）は「準備時に適用」と
   原作に明記されている**。したがって携帯起点の可能性がある挙動は**タップの CS 修正に特有**である
   可能性が高い（2026-07-02）。

**実装方針（2026-07-02 確定・[Active_Effects.md](../Game_Mechanics/Active_Effects.md) 大原則5）**:
パラメータによる修正は直接読み取り適用。**パラメータの特殊挙動（少なくともゴースト登場時の CS 修正無視）も
AE を使わず直接読み取りロジック側の条件で処理**する。AE は「完全に解説由来の挙動」と「『CS：0（+1）』のような
同例のほぼない個別事象（仕方なく）」に限る。したがって——
- タップの CS 修正パラメータは**直接読み取り**（`computeOutfitAggregates`）で適用し、
  **ゴースト時無視（`!isGhost`）も同ロジック内のゲートとして維持**する（AE に外出ししない）。
- **適用は「ゴースト時は適用しない」フラグで一元化（2026-07-02 ユーザー裁定・確定＝最終形）**:
  タップの CS 欄の下段に**「ゴースト時は適用しない」チェック**を置く（スタイル技能「対象」の
  「変更不可（※）」チェックと同形式）。このフラグが**携帯起点とゴースト時無視の両方**のスイッチになる。
  - **OFF（既定）**: 通常原則どおり**準備済みでのみ適用**し、**ゴースト登場に関係なく適用**する。
    ＝完全にフラットな通常パラメータ（オリジナルデータはここが基準。ゴースト無関係のマイナス修正も
    表現できる）。
  - **ON**: **携帯時点で適用**し、**ゴースト登場中は無視**する。**説明タブの表示項目を（）で囲む**
    （原作の「CS：（-20）」括弧書き表記の再現＝括弧はこのフラグの表示形式）。
  - 公式タップの非 0 CS 修正は全て括弧書きのマイナス（事実4）→ **ON で入力**する運用。
  - 根拠: この修正は設定上「持ち運びにくい（もしくは持ち運べないほど大きい）タップに遠隔で接続しながら
    シーンに登場することによる負担」＝物理的携行の帰結（携帯起点・体がシーンに無ければ消える）。
    防具・ヴィークルの制御値修正は「準備時適用」と明記（事実5）＝この挙動は**タップの CS 修正に限定**。
  - ＋の値も扱いは同じ（フラグ OFF なら準備起点・ゴースト適用。現存データが無い以上、オリジナル
    データのためになるべくフラットにしておく＝2026-07-02 確定）。
- **「無視」の解釈による整合（2026-07-02 ユーザー裁定・ルール上のつじつま合わせ）**: 原作の文言は
  「ゴースト登場時は**無視**」「不携帯であれば**考慮する必要は無い**」であり、「不適用」とはニュアンスが
  異なる。そこで——フラグ ON の CS 修正は（携帯という、プレアクトに確定する装備状態を前提に）
  **プレアクト時点で CSベースに乗り、CS にもそのまま焼き込まれる**。アクト中に付け外しされる動的な
  修正ではない。ゴースト登場・不携帯宣言の場面では、焼き込まれた修正を**参照時に読み飛ばす
  （無かったものとして扱う）**——CSベース／CS の再計算ではない。これにより「CS はプレアクト決定・
  再計算されない」のスナップショット原則とシーン単位の扱いが両立し、事実2の「携帯して登場した際」も
  動的トリガーでなく**「実際に意味を持つ場面」の記述**と読める（誤表記と断ずる必要がなくなる）。
  括弧書き「CS：（-20）」は「焼き込まれているが場面により読み飛ばせる部分」の標示として整合する。
  ※**実挙動（参照時に読み飛ばす仕組みの実装）は本裁定の対象外**＝10-5／13 で設計する。
- **据え置き型の識別フラグは不要**（このフラグで表現できる。解説文からの推測もしない＝§4.2）。
- 実装はフェーズ10-5（KI-010・CS パイプライン・AE の CS 3層着地キー＝[Active_Effects.md](../Game_Mechanics/Active_Effects.md)
  大原則6 と併せて）。現行の「携帯起点＋一律 `!isGhost`」は**フラグ駆動へ置換**する（公式タップは ON 入力
  なので実運用の挙動は互換）。タップへのフィールド追加（ゴースト時無視フラグ）は §4.3 の一括承認対象
  （ユーザー発案 2026-07-02）。

## ヴィークル（vehicle）（2026-06-13 確定）

- **speedFactor — 移動力（略号 SF）**: 数字分の段階移動ができる。キャラクターの通常移動が
  一段階移動なので、SF1 のヴィークルは戦闘移動としては生身と同程度

### ヴィークルの防御力・攻撃力（2026-07-09 ユーザー確定・実装済み）

- **防御力（搭乗中は加算）**: 準備済み（搭乗中）ヴィークルの防御力は、戦闘タブの防御力合計に **armor/義体と同様に加算**される（`_prepareCombatData` の combatDefenceTotal に `vehicle` を追加）。※個人防具＋ヴィークル防御力の上乗せ扱い（ユーザー報告「加算されない」→加算で修正）。厳密な適用（義体の一種のみ等）は 12 の実効防御派生に委ねる。
- **攻撃力（ヴィークルを武器として使う）**: ヴィークルは attack を持つが、**攻撃力参照（現在の生身）の候補には出さない**（＝正しい。ヴィークルでの攻撃は特定のスタイル技能でしか行えない制約付きアクションで、既定攻撃の書き換え元ではない）。代わりに、その制約を持つ**スタイル技能に攻撃用途（check+damageCategory）を持たせ、`weaponRefs` にヴィークルを参照**する。攻撃用途の武器参照候補を武器＋ヴィークルに拡張済み。これで制約（その用途からのみヴィークル攻撃可）を保ったまま既存の攻撃パイプラインを使える。

### 搭乗・同乗の状態管理（2026-07-09 ユーザー指摘 → 同日 リアクター汎用化で解決）

- **搭乗判定**: ヴィークルを**準備済み(prepared)かどうか**で「そのヴィークルに搭乗している」と判定する（2026-07-09 ユーザー確定。部位「操縦」は1枠のため準備ヴィークルは常に1つ）。
- **搭乗中のリアクション＝対決が「〈操縦〉※」になる（2026-07-17 ユーザー確定・実装済み `238d775`）**: ヴィークルを操縦しているキャラクターに対する判定は、そのリアクターについて対決が自動的に**「〈操縦〉※」**へ置き換わる（リアクター側状態由来・対決の唯一の特殊処理。「不可」マスクは残す=Code 設計）。対応する操縦技能（レベル1以上）を持たなければリアクション不可。※旧「回避→操縦のハード上書き＋操縦なしはパリー/制御値受けフォールバック」（2026-07-10）はこの規約に置き換えられた（[Check_Rules.md](Check_Rules.md)「対決の解釈（是正 2026-07-17）」）。
- **同乗者への攻撃のドッジ**: 同乗者を攻撃されたとき、ドッジは**操縦者が**（同乗者本人でなく）**操縦**で行う。
- **解決（occupancy モデルは作らない）**: 当初「どのアクターがどのヴィークルに乗り誰が操縦者か」を保持する乗車関係(occupancy)モデルが要ると考えたが、**過剰**と判断（ユーザー確定 2026-07-09）。実際に必要なのは「**リアクションの実行アクター(リアクター)を攻撃対象から切り離す**」一点のみ。他者の被攻撃に代理反応できる技能は操縦以外にも複数存在するため、汎用の仕組みとして解決する。
  - 実装（`attack-flow.mjs`・2026-07-09）: ドッジ/パリー/リアクションの導線を**全員に開放**し、押下時に**リアクター＝選択トークン→割り当てキャラクター**を解決、**権限が無ければ弾く**（GM は常に可）。判定はリアクター自身の技能・値・報酬点・AR/パリー武器で行い、対決の命中結果は従来どおり攻撃対象(f.targetUuid)に返る（ダメージも対象へ）。
  - 「リアクションしない」だけは**対象自身の宣言**（制御値で受ける）なので、対象の操作者か GM に限定（`handleNoReaction`）。
  - 卓の手動運用を信頼する設計（攻撃対象選択の「対象なし」許容と同思想）。誰が同乗しているかはデータで持たず、操縦者の操作者がその場でドッジを宣言すれば足りる。

### ヴィークル操縦移動（2026-07-09 ユーザー確定 → 2026-07-17 移動タイプ用途へ再編・実装済み `238d775`）

- **操縦中はメジャーアクションでも移動できる**。対応する〈操縦〉で判定を行い、その**達成値÷10 段階**（**端数切り捨て**＝2026-07-09 ユーザー確定）の移動が可能。ファンブル/スート不一致は達成値 0 として 0 段階。
- **モデル（2026-07-17 再編: 〈操縦〉技能の「移動」タイプ用途）**: 旧・戦闘タブの合成アクション（`startVehicleMove`）は廃止し、**〈操縦〉技能の移動タイプ用途**（timing=メジャー）に一本化。戦闘タブのタイミング節は**用途の timing で束ねる用途起動ボタン**になったため、2026-07-09 当時の却下理由（用途はアイテム単位 timing に縛られる）は解消した。正準名移行が既存の操縦技能へ移動用途＋リアクション（移動妨害）用途を自動追加する。
  - **使用ヴィークル（2026-07-17 ユーザー確定）**: 移動/リアクション（移動妨害）用途は**準備済みヴィークルの単一参照**（空=実行時に自動解決）。**準備済みヴィークルが無ければ判定できない**（実行時ブロック）。
  - **移動へのリアクション**: 移動用途の対決既定＝「リアクション（移動妨害）」行。対決欄に有効行のある移動は**対決判定カード**（対象なし=オープンリアクション・先着解決・リアクション側勝利で移動失敗=移動不可）に乗り、移動段階の行を条件表示する。対決欄が空なら従来どおりの移動結果カード（`vehicle-move-card.hbs`）。
- **対応する操縦（ヴィークルに持たせる＝ユーザー確定）**: ヴィークル DataModel に `operateSkillKey`（辞典 `operate_` 技能の `identificationKey`）を追加。ヴィークルシートのプルダウンは辞典一般技能の固有名詞小分類 prefix=`operate` を表示（`loadOnomasticChoices("operate")`）。搭乗中のリアクション＝対決「〈操縦〉※」の解決にも同キーを使う。
- **段階移動の適用は後付け**: 「達成値÷10 段動く」という**移動の適用**は移動・位置（段階/概念戦闘の距離）の機構に依存する。本実装は判定起動と段階数の提示まで（＝FS判定の進行値と同型: 判定は今／効果適用は担当機構が入ってから。反射的なフェーズ先送りでなく位置機構という具体的依存）。

  電脳セキュリティ/アナログセキュリティ/スロット）。住宅施設の基本値に加算した実効値を説明タブに表示する
- **住宅エリアの設定方法**: 住宅施設シートに (a) 住宅エリア辞典（compendium `housing-areas`）からの
  ドロップダウン、(b) アイテムのドロップ の 2 方式。(b) で設定した場合 (a) は無効化。
  住宅エリアはアウトフィットでないためアクターシートへのドロップは弾く（2026-06-13 確定）
- 住宅施設の概要表記順は **購/隠/登場/セ(電／ア)/ス/部位**。
  **危険値と電制がない**（特に危険値は他種別では隠匿値とセットだが住宅施設にはない。隠は隠匿値のみ表記）
- **住宅オプション・住宅アクセサリは一般アウトフィット（general）**。住宅オプションはスロットを
  消費するが、住宅アクセサリはスロット数に関係なくいくつでも準備できる（部位占有の**非消費3型**の
  一つとして実装済み＝フェーズ10-1。準備数の上限管理は存在しない）

## コンバイナー（combiner）（2026-06-13 確定）

- 指定された特徴を持つ**二つのアウトフィットを組み合わせて一つのアウトフィットとして扱う**
- コンバイン後の見た目はどちらか片方のものとなる
- **部位**はコンバイン元両方の指定部位を全て占有する
- **分類**もコンバイン元両方を引き継ぎ、二つの分類を同時に持つ
- **電制**はどちらか高い方
- **隠匿値**は「隠：X(Y)」の形。X = 見た目に設定したアウトフィットの隠匿値、
  Y = コンバイナー本体の隠匿値。Y を目標値に〈知覚〉判定を行うとコンバイン元両方のアウトフィットがわかる
- その他のパラメータ: 両方にあればどちらか好きな方、片方にしかなければそのまま適用
- **コンバイナー本体のパラメータは完全に一般アウトフィットのもの**
- コンバイン条件は**ルール上は選択を制限するが、実装上は自由選択**（条件が細かく将来のコンバイナー
  追加で選択肢追加が必要になるため。2026-06-13 確定）
- アクターへのインポート時は**一つのアイテムとしてインポート**（元アイテムも展開可能にしつつ）。
  名前は「見た目のアイテム名（コンバイン）」形式 → フェーズ6-6（キャストシート）で実装
- **合成時の部位表記はルールブックの表記法則「部位：部位1+部位2」**（両方の部位を占有・「+」連結。
  2026-07-02 修正——旧実装の「、」連結は誤り）
- 実装状況（2026-07-02 更新）: combine{source1, source2, appearance} 構造・元二つのドロップ指定・
  見た目ラジオ・コンバインプレビュー（6-4）、**param 取捨選択 UI**（6-4・`5bb2455`＝両方に値があり
  食い違う項目のみラジオ）、**アクター一体インポート**（コンバイナー＋両ソースの3アイテム一括
  インポート・活性化・「見た目名（コンバイン）」表示・合成列値・リンク解除）まで**すべて実装済み**。

## スロット（extensible）（2026-06-12 確定）

- 装備される側のスロットに名前は基本的にない（一律「スロット」）
- 例外: IANUS の**意識スロット**は「表層意識」「深層意識」「無意識」の 3 種（通常スロットとは別に持つ）、
  タップは**ソフトウェアスロット**・**ハードウェアスロット**のみ名前があり呼び分ける
- **スロットを持つアイテム側はスロット数のみを設定する**（装備状態は持たない）
- オプションを装備した状態で取得されることはないため、装備連携はシート上で用意すれば十分
- 「アイテム名」指定のオプションは、スロットがないアイテムに装備される特殊例。対象アウトフィット
  （スロットなし）を準備している時に限り、対象1つにつき1個だけ準備可能。**便宜スロット `outfitName`（アイテム名・容量1）** で表現し、占有計算でその1枠を消費する（2026-07-23 再設計＝旧「名前照合の別系統」を占有の一種へ統合。1個制限は容量1の超過で自動的に効く。上記「部位管理」の便宜スロット節）
- DataModel 表現: `slots[]: { kind: normal/surface/deep/unconscious/software/hardware, count }`。
  型ごとの既定プール: weapon/tron/vehicle/residence = normal のみ、ianus = normal + 意識 3 種、
  tap = software + hardware。**`outfitName` は仮想スロット**で `slots[]` には保存されず（既定プールにも入れない）、オプション側 `parentSlotKind` としてのみ現れる。

### オプションの準備ゲート（2026-07-23 ユーザー確定）

**オプションは装備先（親＝`parentItemId`）が準備済みでなければ準備できない**（`isOption` 行の規則の具体化）。旧来は部位を1行でも設定した時点で準備トグルが出て既定 ON になり、ホストの準備状態と無関係に単独で準備扱いになっていた。

- **実効フラグ `isPreparedEffective`**（アクター `prepareDerivedData` の `_prepareOptionPreparedGate` で派生）＝保存 `isPrepared` かつ装備先が存在し準備済み。非オプションは `isPrepared` と同値。占有・入れ子表示・戦闘の使用可否・準備トグルの活性表示はこの**実効値**を読む（AE・削除など非トグル経路でも状態が古くならない安全網）。
- **トグルのゲート**（シート `_onToggleOutfitFlag`）: 装備先が未準備ならオプションを準備 ON にできない（`isCarrying` 前提と同様）。準備トグルは装備先未準備のとき**無効化**。
- **連動解除**: ホスト（非オプション）を準備解除（または携帯解除→準備解除）したら、配下の準備済みオプションも自動で準備解除する。
- 正本: Check_Rules ではなく本節。実装は `character-base.mjs`／`tnx-character-sheet-base.mjs`。

## カテゴリ（大分類 → 小分類 → Item type 対応）

全キー・表示名・対応型・保存先は [アウトフィット分類キー一覧](../Documents/Outfit_Category_Keys.md) を参照（大分類8種・小分類40種）。実装上の正本は `scripts/data/item/outfit-categories.mjs`。

主分類と複数の副分類を持てる。大分類・小分類には「解説参照」(`reference`) と「その他」(`other`) を追加し、その他では自由記述欄を表示する。選択肢は通常分類の後に解説参照・その他を並べる。型から分類が決まるアウトフィットもプルダウンを無効化しない。分類の編集でItem typeやDataModelは変更しない。

分類・部位をAEで個別変更する場合は [行操作AE](../Game_Mechanics/Active_Effects.md) を使う。主分類は `primary`、副分類・部位は各行の `rowId` で指定する。旧 `system.additionalCategories` / `system.equip.parts` の上書きは配列全体が対象なので、個別行の変更と区別する。

### パラメータの解説参照

共通の `{mode,value}`、受け値、防御力のmodeに `reference` を追加。攻撃力は `attack.damageType`、射程は `range.min` / `range.max`、攻撃範囲は `attackArea`、式神タイプは `shikiType` に `reference` を保存する。数値未確定を0へ読み替えず「解説参照」と表示する。分類の「その他」の本文も保持する。解説から効果やAEを自動生成する機能ではない。

## 略号グリッドのセル幅配置（2026-08-31 確定）

概要（略号行）のセル幅はルルブ実紙面の配置を型ごとに固定で踏襲する（正本=ユーザー提供のルルブページ p34/62/88/91/120/126/129/145/171/241）。幅は3種: **1/2幅ペア**（既定）・**1/3幅3連**・**全幅（1行1セル）**。目的はスラッシュ区切りの複合値（防・セ・購など）を行の折返しで途中分割しないこと。

| 型 | 配置（行ごと） |
|---|---|
| 武器 | 購\|隠 / 攻\|受 / 射\|ス / 電制\|部位 |
| 防具 | 購\|隠 / **防(S／P／I)=全幅** / 制\|電制 / **部位=全幅** |
| 全身義体 | 購\|隠 / **防=全幅** / 攻\|受 / 電制\|部位 |
| IANUS | 購\|隠 / ス\|表 / 深\|無 / 制\|部位 |
| トロン | 購\|隠 / ス\|電制 / **部位=全幅** |
| タップ | 購\|隠 / **サ=全幅** / **ソ\|ハ\|CS=1/3幅3連** / 電制\|部位 |
| ヴィークル | 購\|隠 / 攻\|SF / **防=全幅** / 制\|乗員 / ス\|電制 / **部位=全幅** |
| 住宅 | 購\|隠 / **登場=全幅** / **セ(電／ア)=全幅** / ス\|部位 |
| 最小単位（一般/コンバイナ） | **購\|隠\|電制=1/3幅3連** / **部位=全幅**（p91 ニューラルウェアの形式） |
| 式神装備 | 上記に加え **タイプ=全幅・部位=全幅**（p241 STYLE SECTION の形式） |

- 部位は「常に全幅」ではない（2026-08-31 裁定）。武器・義体・IANUS・タップ・住宅では 1/2 ペアの一員（ルルブ実紙面どおり）。
- 溢れの逃がし（表示側 fit・2026-08-31 改定）: 値は nowrap とし、セル幅に入りきらない場合は**値のみ文字幅を scaleX 圧縮**して収める（ラベルは縮めない・セルの行送り＝全幅昇格はしない。当初の昇格/格下げ方式はユーザー指示で撤回）。適用はツールチップ・辞典ブラウザの両方。
- 適用範囲: 辞典ブラウザのカード・アイテムツールチップ・アイテムシート説明タブの3読者すべて（実装は `buildOutfitSummaryRows` の width 指定＋6分割グリッド CSS＋`fitDictionaryCard` 第0段）。

### 住宅施設のセキュリティの「なし」

電脳・アナログは、それぞれ `cyberSecurityMode` / `analogSecurityMode` で `none`（なし）、`value`（数値）、`reference`（解説参照）を選択する。既定は `value` で、既存データの数値を維持する。
数値本体とAEのキーは従来の `cyberSecurity` / `analogSecurity` のまま。数値モード以外では表示を「-」「解説参照」とし、住宅エリアを含む実効数値は null として扱う。
インポート時の `－/7` は電脳なし・アナログ7、`0/0` は両方とも数値0であり、区別する。
