# アクト進行（シナリオ進行）

TNX のアクト（シナリオ）進行に関するルール解釈の正本。フェーズ8 後の設計議論で言語化・確定（2026-06-19）。

1アクト＝1シナリオは **アンダーワーク → プレアクト → メインアクト → ポストアクト** の流れで進む。メインアクトはシーンの連なり（**シーン進行**）で構成され、戦闘時はその中で[カット進行](Combat_Flow.md)が行われる。

## 1. アンダーワーク（事前準備）

アクト運営のための事前準備全般。厳密にはアクトの流れの外。ハンドアウトの事前配布、シナリオ準備、トレーラー準備、新規キャストの作成などが含まれる。

## 2. プレアクト（直前準備）

アクト直前に行う準備。主な処理：

- アクトトレーラーの読み上げ、ハンドアウトの配布・読み上げ（配布は事前に済んでいることが多い）
- **ペルソナ・キーの決定**（→ [Character_Creation.md](Character_Creation.md) のスタイル役割）
- **市民ランクの決定**
- **報酬点の取得**（→ [Bounty_Points.md](Bounty_Points.md)）
- **CS の決定**（CSベースから CS を確定。→ [Combat_Flow.md](Combat_Flow.md) の CS）
- **アクトコネクション**の取得（経験点なし・そのアクト限定のコネ技能。ハンドアウト指定 NPC とのコネと、キャスト間コネクションの2種）
- ハンドアウトの構造（2026-08-08〜09 ユーザー指摘で確定）: **コネ欄＝アクトコネそのもの**（別欄にしない・**必ず一つ**）・**推奨スートはコネに付随する情報**（コネ行に対で置く）・**指定スタイルはコネと無関係の独立項目で、「推奨」ではなく必ず取得するもの**（スタイル辞典のプルダウン）。**ハンドアウトはユーザーに付与される**（参照はキャストでなくユーザー・自動設定はユーザーの割当キャストから解決・対象ユーザー欄はハンドアウト自体の内容ではないため最下部）。**名前は「①〈スタイル名〉用ハンドアウト」形式**（番号は前置・自動生成。「共通」＝共通ハンドアウト（番号なし）・「自由記述」＝自由入力。PC名欄は持たない）
- プレイヤーの**切り札**配布、各**山札**の準備（FVTT で未準備なら）
- **PS**（Purpose in this Scenario＝キャストごとのシナリオ上の目的・目標）の配布

## 3. メインアクト

**オープニング → リサーチ → クライマックス → エンディング**の4フェイズで構成。各フェイズはシーンで区切られる（**シーン進行**）。

### シーン進行

- シーンは特定の時間・場所に縛られない。
- RL がシーン開始を宣言 → **シーンプレイヤーの指定**と**シーンカードの提示**。
- シーンプレイヤー以外で登場したいキャラクターは**登場判定**を行う（**1シーンにつき1回**・2026-08-22 ユーザー。システムは回数を制限しない＝卓運用・登場中は振れない）。チームを組んでいる場合の登場資格と運用（登場時に判定を行い成否不問で登場可能・適用は RL の操作＝「チームで登場」機能は 2026-08-22 にオミット）は [Appearance_Check.md](Appearance_Check.md)「チームと登場の運用」を正本とする。
- **チームを組む宣言はいつでも可能**（シーンに登場していないキャスト同士でも可）。**チームにはゲストを入れることもできる**（2026-08-08 ユーザー裁定）。
- **RL は登場判定なしで任意のキャラクター（キャスト／ゲスト／トループ／エキストラ）を登場・退場させられる**（2026-08-09 ユーザー裁定）。名前を伏せて登場させる指定があり、卓には「？？？」と表示される。台本のシーン行に**登場キャラクターを事前設定**しておくこともできる。→ [Appearance_Check.md](Appearance_Check.md)
- シーンは **RL の宣言で終了**する。
- **ルーラーシーン**（2026-08-08 ユーザー・※「マスターシーン」ではない）: RL が進行するシーン。**ルーラーはプレイヤーではないため、ルーラーシーンにシーンプレイヤーはいない**。表示も「シーンプレイヤー：なし」等でなく**「ルーラーシーン」とだけ**書く。
  - **指定はシーンプレイヤー欄の独立した選択肢「ルーラーシーン」**（2026-08-10 ユーザー裁定）。~~GM ユーザーを選択＝ルーラーシーン~~（14-7）は**撤回**——1つの選択で「誰がシーンプレイヤーか」と「ルーラーシーンか」の2つを表していたため、**RL がキャストを持ちハンドアウトの割り当てもある場合に、その RL のキャストを主役にできなかった**（必ずルーラーシーン扱いになった）。GM ユーザーの選択は「その RL のキャストが主役」を意味する。
- **シーンプレイヤーの指定はハンドアウトで行う**（2026-08-10 ユーザー指摘）。**通常のシナリオは「SCENE 2：シーンプレイヤー＝HO①」の形で書かれ**、誰がそのハンドアウトを担当するかはプレアクトで決まる。台本にユーザーやキャストを直接書くと、担当が変わるたびに台本を書き直すことになり、巡回シーン（ハンドアウト順に回す）とも通貨が揃わない。
  - 実行時は **ハンドアウト → 対象ユーザー → 割当キャスト** の順に解決する。担当が解決できない指定は警告し、そのシーンはシーンプレイヤー不在として扱う。
  - 台本の欄の表記は **「①スタイル名（キャスト名）」**、キャスト未設定なら「①スタイル名」。自由記述ハンドアウトは自由入力のタイトルを使う。**共通ハンドアウトは候補に出さない**（全員向けなのでシーンプレイヤーになり得ない）。

### シーンの種別（2026-08-09 ユーザー・14-8）

**シナリオの形式は一様ではない。** 想定されるシーンをすべて厳密に決めているシナリオもあれば、**特定のイベント以外は固定の登場判定目標値もシーンプレイヤーも持たないリサーチシーンが続く**シナリオもある（基本はハンドアウトの1番目から順にシーンプレイヤーを回し、条件を踏んだところでイベントシーンが起動する形式）。台本の行に**種別**を持たせて両方を表す。

| 種別 | 内容 |
|---|---|
| **通常シーン** | 従来どおり、台本で全て決めておくシーン |
| **巡回シーン** | 同じ行に何度でも入場する。入場のたびにシーンプレイヤーが**ハンドアウト順の未消化の先頭**へ進む。エリア・登場判定目標値は台本で決めず、シーン開始時にその場で決める |
| **イベントシーン** | **起動条件**（テキスト・自動判定はしない）を持ち、条件を踏んだと RL が判断したときに割り込ませるシーン |

- **巡回の正本は「位置」ではなく「誰がまだシーンプレイヤーをしていないか」。** イベントシーンでシーンプレイヤーを務めた者はその分が消化されるので、**順番は飛ぶ**（「なるべくシーンプレイヤーをしていないプレイヤーに回してあげる必要がある」ため）。既定は未消化の先頭だが、RL は選び直せる。
- **消化は「リサーチのシーン」だけを数える**（2026-08-10 ユーザー指示）。オープニングのシーンプレイヤーは巡回の消化に含めない。記録のクリアは**全員が務め終えたとき（＝次の巡）**と、アクトの読み込み・開始のみ。
- **巡回の候補＝ハンドアウト順のユーザーのうち、キャストを割り当てている人**（2026-08-10 ユーザー裁定）。キャストが無ければシーンプレイヤーになれない＝そもそもアクトに参加していないので落とす。**GM かどうかは見ない**——RL がキャストを持ちハンドアウトの割り当てもあるなら、その人は巡回の正当な参加者。巡回シーンに「ルーラーシーン」の選択肢は出さない（巡回にルーラーシーンはあり得ない）。
- **巡回シーンの舞台**（シーン開始ダイアログで選ぶ）: 「任意」（エリアと登場判定目標値を直に指定・目標値の初期値は 10）か、**シーンプレイヤーのキャストと登場キャラクター、またはそれらとチームを組んでいるキャラクターが所持している住宅施設**。住宅施設は登場判定目標値とエリアをそもそも持っているので、舞台にしたシーンはその2つを自動で読み取って適用する（→ [Appearance_Check.md](Appearance_Check.md)）。
- **イベントを終えて巡回に戻したい場合は、台本に巡回シーンをもう一度置く。** 台本は `[巡回][イベント…][巡回][イベント…][クライマックス]` の形になる。イベントは複数の候補から1つを選んで起動する——想定と違う順番でイベントを巡るシナリオがあり得るため（候補の範囲は下記）。
- **イベントシーンは実行済みフラグを持つ**（開始時に立つ）。**リサーチのイベントが全て実行済みになったらクライマックスへ進める。** 踏まれずに終わったイベントは「起動せず実行済みにする」で消化できる。
- 「次のシーンへ」は、**イベントシーンから未実行のイベントシーンへ送る形になるときだけ出さない**（起動条件を踏んでいないイベントへ順送りで滑り込ませないため）。**実行済みのイベント行は読み飛ばす**——もう一度入る意味が無く、飛ばさないと消化しきったイベント群の中で送り先が無くなる。リサーチ先頭のイベントは、オープニングからの「次のシーンへ」で普通に起動する。
- **未実行のイベントは、どこからでも起動できなければならない**（2026-08-09 ユーザー）。連続したイベント群の一番下にいても、リサーチ末尾の巡回シーンにいても、**それより上に残った未実行のイベント**は「イベントシーンを起動する」の候補に出る。候補は台本順に並び、**初期選択は最も上にある未実行のイベント**。次の巡回シーンを越えた先のイベントは候補にしない（先の段階のイベントのため）。
- **上演中のシーン番号は自動カウント**（2026-08-09 ユーザー）。巡回シーンを含むアクトではオープニング以降のシーン数が変動するため、台本の行番号ではなく**シーンに入るたびに +1 する「何シーン目か」**を「SCENE n」として出す（巡回シーンの再入場も1シーンと数える）。台本側の No. は台本順の自動採番（手入力はしない）。

> カット進行（戦闘）も独立した1シーンとして、このシーン開始処理で始まる（Combat_Flow の「1. カット進行の開始」の参照先）。

### 各フェイズ

- **オープニング**: 各キャストがアクトに関わるきっかけを描写。基本、シーンプレイヤー以外は登場不可が多い（複数キャスト同時オープニングもある）。
- **リサーチ**: 他キャストと出会い、情報項目を調査し、誰をどう倒すかを決定する。情報項目の調査＝**情報収集判定**（基本は舞台裏。シーン中も可。基本1シーン1回）。シナリオによっては途中の情報で **SPS**（追加 PS）が与えられる。
- **クライマックス**: 得た情報を基に敵を倒す。基本カット進行シーン1つで終了（連続2シーンの戦闘や準備シーン挿入もある）。カット進行のシーンプレイヤー指定は RL 判断。
- **エンディング**: 各キャストの結末を描写。キャストごと1シーンずつが普通。

### 情報項目の構造（2026-08-12 ユーザー）

情報項目で公開される内容の増え方には**2種類**ある。

> 「同じ項目でも要求技能が違う場合と目標値で内容が増える場合の2種類がある」（2026-08-12 ユーザー）

| 種類 | 意味 | 表現 |
|---|---|---|
| **要求技能が違う** | 別の技能で調べると別の内容が判明する（並列） | 情報項目の中に**内容ブロック（枝）を分ける**。枝が自分の使用技能（技能の集合＋目標値の行）を持つ |
| **目標値で内容が増える** | 同じ技能のまま、目標値ごとに別の内容が判明する | 枝が**目標値を複数持つ**。各目標値が本文を持ち、使用技能は枝から引き継ぐ |

- 到達した目標値以下の内容も**併せて得る**（累積）。
- 目標値ごとに要求技能が変わることは**ない**——要求技能が変わればそれは別の枝であり、内容ブロックそのものを分ける（2026-08-12 ユーザー指摘）。
- **目標値は達成値の絶対値と比べる**（Code 提案・2026-08-12 ユーザー承認）。枝が「〈情報：ストリート〉8／〈情報：ネットワーク〉10」のように入口ごとに違う目標値を持っていても、「12」はどちらの入口から入ったかを問わない。

#### 目標値どうしの関係（2026-08-15 ユーザー）

> 「あくまでも各目標値で出る情報は等価であり、下の段が追加情報という事実はありません。しかも、むしろ扱いとしては一番高い目標値が通常の目標値です。低い目標値はあくまでもどうしても達成値が出ないときのためのもので、情報の内容的にも、ほとんどのシナリオで、一番上まで突破することが想定された作りになっています」（2026-08-15 ユーザー）

> 「こういうことを言うとあなたは一番高い目標値を逆に権威的に扱おうとするでしょうが、それもやめてください。（略）全ての情報は表示の上では等価です」（同）

- **低い目標値＝主・高い目標値＝追加**という関係は**無い**。逆に**高い目標値を主役に格上げするのも誤り**。
- したがって **UI・チャットでは全ての目標値を同列に置く**。「さらに」「追加で判明する」等の順位を示す語・入れ子・字下げの差を付けない（一番上に置くのは**指定技能だけ**で、目標値はその下に同じ深さで並ぶ）。
- 実装上の呼称（`content.tiers`）は保存形式の都合であり、**表示にも用語にも出さない**。

実装（`content.tiers`・開示の累積・シート/パネルの表現）は [Phase_14_Tasks_Detail](../Phases/Phase_14_Tasks_Detail.md) 14-8 を参照。

#### 情報項目のチャット送信（2026-08-15 ユーザー）

送信は**2 つの意味**を持ち、出すものが違う。

> 「元々は情報項目名と技能、目標値のみで本文は送っていなかったはずです」（2026-08-15 ユーザー）

| 送信 | いつ | 卓に出るもの | 体裁 |
|---|---|---|---|
| **目標値の送信** | 開示済みの内容が 1 つも無いとき | 情報項目名・使用技能・目標値**のみ**（本文は出さない） | 指定技能の行に目標値を**横並び**：`〈社会：ストリート、警察〉目標値: 8, 12, 15` |
| **開示済みの送信** | 開示済みの内容があるとき | 開いている目標値の本文 | **目標値｜本文**の 2 列（罫線の無い表＝公式 SSS・PDF の紙面と同じ体裁） |

- 目標値の送信は「**何がどの目標値で判るか**」の提示であり、未開示の内容を卓に出すものではない。
- **非公開の情報は送信できない**（2026-08-18 ユーザー指示）: 送信ボタンは**公開状態にして初めて出る**（非公開＝技能・目標値も伏せる段階なので、送るものが存在しない）。
- 体裁はいずれも 2026-08-15 ユーザー指定。開示済みの送信の例:

```
〈社会：テクノロジー〉
 5  自らを“氷の静謐”と名乗り終末思想を謳う真教から派生した宗教結社。……
10  能天使と呼ばれる幹部及び熱心な信徒達で構成され、……
12  内部において組織だった抵抗を見込んでいないのは、……
```

- 目標値を持たない行は出さない（出すものが無い）。
- **未開示の残りの併記**（2026-08-25 ユーザー指示・verbatim「未開示の情報がある場合は、公開されている情報の下に表示してください。形式は完全に未開示の時と同様です」）: 開示済みの表示（手動送信・ツールチップ・判定成功の自動公開カード）では、未開示の目標値が残っている限り、**開いている本文の下に「目標値の送信」と同じ形式**（技能行＋目標値の横並び・本文なし）で併記する。開示が始まっても「残りを何の技能・目標値で抜けるか」が表示から消えない。
- **判定成功の自動公開**（2026-08-25・Code 提案をユーザー承認）: 判定成功で新規に開示があったとき、**今回新たに判明した分だけ**を開示済みの送信と同じ体裁で自動送信する（全開示済みの再掲はツールチップと手動送信が担う）。新規開示が無ければ送らない（再判定の単調適用で重複しない）。

#### 情報収集判定の裁定（2026-08-16 ユーザー・フェーズ14-9）

情報項目の公開状態は**3段階**。

| 段階 | 卓（PL）に見えるもの | 備考 |
|---|---|---|
| **非公開** | 項目の**存在のみ**（「非公開の情報」として表示） | 技能・目標値・内容とも伏せる。「『非公開』は本来技能や目標値も非公開の段階」（ユーザー） |
| **公開** | 項目名・使用技能・目標値 | 判定を試みられる状態 |
| **開示** | 内容（本文・段） | 内容ブロック/段ごと（既存の開示チェック） |

- **判定成功時は自動で開示する**（RL の承認を挟まない）。
- **達成値が抜いた目標値まで一括開示**（届いた段まで全部開く）。
- **回数制限は設けない**——「そういうことは今後も他の機能でもしません」（verbatim）。卓運用の「基本1シーン1回」（上記リサーチの項）は卓が守るものであり、システムは回数を制限しない（[Check_Rules](Check_Rules.md)「判定そのものはブロックしない」と同じ系統の原則）。
- **情報項目は HUD に表示する**（非公開の項目も「非公開の情報」として存在は見せる）。
- **ツールチップは常設**（2026-08-16 追加裁定）: 「開示された情報はいつでもツールチップで確認できるべき」。開示済みの項目はその内容、**未開示でも指定技能と目標値**をツールチップで見せる——「万が一チャットが流れていった場合に備えて」（送信カードと同じ組み立て・チャットカード意匠）。
- **判定の起動ボタンは項目に1つ**（2026-08-16 追加裁定）: 技能行ごとにボタンを並べない。特定の技能でないと抜けない情報を含む項目では、ダイアログでどれで挑むかを選ばせる。
  - **選択はダイアログ1回**（2026-08-25 是正・ユーザー指摘「三回も『この技能で判定』を選ばされるのは明らかに不自然で設計ミス」）: 従来の「技能行を選ぶ→行内の指定技能を選ぶ」の多段を廃止。
  - **形式は縦積みボタン＋4系統の選択肢**（2026-08-25/26 裁定で再是正・正本は [Check_System](../Game_Mechanics/Check_System.md)「指定技能への応答」）: 「〈技能名〉で判定する（目標値 n）」ボタン群（未所持指定はグレーアウト）＋代用技能・指定充足の技能＋**代用判定（行=目標値ごとに常設）**＋キャンセル。代用判定が常設になったため「選択肢1つならダイアログなし」の短絡は廃止（応答時は必ずダイアログを1回経る）。
- **帰結行は実適用後**（2026-08-25・KI-042 是正）: 結果カードの「情報を開示した」は、開示が**実際に適用された後**に GM 側が刻む（判定側では出さない＝適用の裏付けなく表示しない）。
- **activeGM 不在は警告**（2026-08-25）: 開示の適用は GM 所有ジャーナルへの書き込みのため activeGM が代行する。不在時は判定をブロックせず、判定者に「開示は適用されない」ことを警告する。

### 舞台裏判定

- シーンに**登場していないプレイヤー**が、**シーンごとに1回**行える判定。
- 「追加の舞台裏判定」を行う効果のスタイル技能で、2回目の舞台裏判定や、登場しつつ舞台裏でも判定する場合がある。
- 社会攻撃・購入判定・情報収集判定などがここで行われる。
- **舞台裏があるのはリサーチのシーンのみ**（2026-08-08 ユーザー確定）。位置づけは**シーンの終了処理の一部**（クリンナップ・プロセス相当）で、進行は「シーンを閉じる → 舞台裏を回す → 次のシーンへ」。**回しきるまで次のシーンへは進めない**（実装＝フェーズ14-6）。舞台裏で何もしないことはできるため、判定の有無・回数にシステムは介入しない。

## 4. ポストアクト

アクト終了処理：

- レコードシートの確認、致死ダメージが残るキャストの**ロスト確認**、残存ダメージの消去、失われた常備化アウトフィット（消費・破壊など）の回復。
- **報酬点の清算**（全て失われ、次アクトに引き継げない）。
- **経験点の算出**。

### 経験点取得条件

経験点はプレイヤー（User）単位で付与される（→ [Experience_Points.md](../Game_Mechanics/Experience_Points.md)）。

**PL**:

| 条件 | 点 |
|---|---|
| ルーラーの依頼を果たした | 1 |
| 会場の手配・連絡などを行った | 1 |
| アクトに最後まで参加した | 5 |
| 良いロールプレイを行った | 5 |
| PS を果たした | 5 |
| SPS を果たした | 5 |
| 他のプレイヤーを助ける言動を行った | 5 |
| アクトの進行を助けた | 5 |
| 上手く神業を使った | 1（1つにつき） |
| シーンに登場した | 1（1シーンにつき、最大5） |

**RL**:
- 会場の手配・連絡などを行った: 1
- `プレイヤーの取得経験点の合計` ÷ `3かプレイヤー人数の小さいほう`（切り捨て・**2026-08-30 ユーザー是正**）
  - 除数が min(3, 人数)。旧記録「`÷3` もしくは `プレイヤー人数` の**少ない方**」（商と人数の min）は誤記録で、v0.15.0 までの実装（`calcRlExpTotal`）はこの誤読のままだった。

> 取得条件には主観的判断（良い RP 等）が多く、自動算出にはなじまない。既存の EXP 計算ロジックは書き換えない（CLAUDE.md §4.2）。

- **卓の運用実態**（2026-08-30 ユーザー言明・verbatim）:「基本的によっぽど厳密に裁定しない限り、経験点の取得条件は全て満たされたものとして配布することがほとんどです」。配布ダイアログの**「全て自動で入力する」**はこれを前提に、チェック8種を全て ON・神業＝そのアクトで消費した回数・登場＝記帳したシーン数（実数・上限5は合計側）で全 PL 行を埋める。記帳は従来どおり「確定」まで行われず、修正は RL の個別操作が最終。
