## 判定の種類

> **用語規約（2026-07-12 ユーザー確定・以前に口頭確定済みだった規約の記録漏れを訂正）**: このゲームで無印の「判定」と言った場合、**能力値判定または技能判定**を指す。**制御判定は常に「制御判定」と明示される**——したがって「判定の～を変更/修正する」系の能力・機構は、明示が無い限り制御判定には掛からない。実装でも無印「判定」対象の機構（スート変更等）は制御判定を対象外とする。

### 能力判定

1. RL が能力値・目標値を宣言（RL 主導。プレイヤー自発はほぼ発生しない）
2. 指定された能力値に対応するスートのカードを手札から出す
3. 達成値 = カード値 + 指定能力値（実効値）
4. 目標値と比較。場合により差分値（達成値 − 目標値）を算出

### 技能判定

1. RL が技能・目標値を宣言
2. 指定技能で使用できるスートのうち好きなスートのカードを手札から出す
3. 判定成立（カードを出した時点）
4. 報酬点の使用を決定（使う場合：1点 = 達成値 +1、消費上限は所持点数のみ）
5. 達成値 = カード値 + 出したスート対応の能力値（実効値）+ 使用報酬点 + 判定バフ + **判定ボーナス**
6. 目標値と比較。場合により差分値を算出

**判定バフ**: AE・コンディション由来の達成値修正（`_computeCheckBonus`＝酩酊/萎縮/憎悪/電子妨害等）。
**2026-11-15 更新：修正値の保存と導出**。用途固有の式・追加行と、参加技能の定義から導出する行を分離する。`source` は帰属表示であり、来歴判定や手動行の削除には使わない。式の評価・重複制御のルールは変更しない。再判定は用途固有入力から技能分を再解決する。旧用途は個別確認まで保存値を維持する。保存形式・移行手順は [用途システムの現行方針](../Game_Mechanics/Usage_System.md) を参照。

**判定ボーナス（2026-07-10 ユーザー確定・実装済み）**: **用途自体が持つ達成値への加算**（D&D の「命中ボーナス」相当だが、攻撃に限らず**全ての判定**に出るため「判定ボーナス」）。`usage.checkBonuses` ＝ **`{formula, source}` の行の配列**。判定時に各行を評価し達成値へ加算、チャット内訳に**供給元名つき**で「判定ボーナス（供給元名）」と表示。
- **式の参照キー**: 能力値は `@abilities.<能力>.value`、技能レベルは `@skill.<識別キー>.level`、アウトフィットは `@outfit.<識別キー>.*`。保持元アウトフィットは `@item.*`、準備先は `@parent.*`。カード値は `@card`、確定後の達成値・差分値は `@achievement` / `@diff`。対象が供給されるダメージ式では `@target.*` も使える。評価時点・素値と実効値・旧キー互換の詳細は [Formula_Reference.md](../Game_Mechanics/Formula_Reference.md) を参照。
- **供給元（source）＝チャットの帰属表示専用**（式の参照とは独立）。識別キーを保存し**表示は逆引きした現在のアイテム名**（生キーは表示しない・`identification.mjs`）。用途シートの供給元プルダウンは**組み合わせスタイル技能（一般技能除外）＋使用武器**をカテゴリでグループ表示、値＝識別キー。空＝「用途」。純ロジック `evaluateBonusRows`。

**状況修正（手動・2026-07-14 ユーザー確定）**: **全ての判定で状況ボーナス／ペナルティを入力できる**。判定ダイアログに常設の number-input-spinner（通常判定＝達成値へ加算・制御判定＝制御値へ加算）。代用判定のペナルティや再判定の引き継ぎ値（スナップショットの `manualMod`）が初期値に入り、調整もできる。内訳は「修正（手動）」行。

**達成値の下限（2026-07-15 ユーザー確定）**: **達成値は 0 未満にならない**。AE のペナルティ・状況修正の負値・判定ボーナスの負値などで**計算途中は負になり得る**が、**最終的な達成値は 0 まで戻す**（下限クランプ）。基本計算（`calcSkillCheck`）と事後修正（`modifyCheck`／GM 手動の達成値修正）の両方で `Math.max(0, …)`。GM 手動ツールは使用自体（タイミング・修正量）を制限しないが、生成される達成値はこの下限に従う＝**負の達成値という不正な値は作れない**。制御判定は達成値を持たない（カード値 ≤ 制御値）ため対象外。

**技能レベルは達成値に加算しない。** 技能レベルが寄与するのは:
- 使用可能なスートの数（レベルが高いほど選択肢が増える）
- 一部スタイル技能・アウトフィットの発動条件・装備条件のみ

**能力値の選択**: 出したカードのスートに対応する能力値が自動的に使われる。
例: ♠♥が使える技能で♥を出した場合 → 生命値が適用。

### 固定値判定（2026-07-03 言語化・2026-07-04 再整理）

- **担い手はエキストラ**（アウトフィットとして取得できるエキストラを含む。小分類「エキストラ」のアウトフィット表記＝〈知覚〉10・〈選択した操縦〉10 等）。**達成値はその固定値**となる（**スート・レベル・カード・能力値を一切読まない**＝技能判定として統一しつつ固定値のみで解決）。
- エキストラのアクターは**固定値判定用の一般技能のみ**持てる（シートは「技能名＋達成値」表示・2026-07-04 → [Actor_Types.md](../Documents/Actor_Types.md)）。通常判定は行えない。
- **実装（フェーズ11-5）**: usage の check 用途の**「固定達成値」**（`fixedResult`・空欄=通常判定。**設定方法は用途とする＝2026-07-04 ユーザー確定**・一般技能アイテムは無改造）。設定された用途の判定はカード選択を経ず、達成値を直接チャットへ出す（flags は通常判定と同じ checkResult 形）。
  - **設定導線（2026-07-04 確定）**: 固定値用途を**作成できるのはエキストラ直下の一般技能のみ**。該当技能の用途タブで「追加」すると選択ダイアログなしで「判定（固定値）」が直接作られる（固定達成値=10 初期値）。用途シートの発動タブは**固定達成値（スピナー）のみ**を表示し、タイミング・対象・射程・目標値・対決等の通常判定項目と効果タブは出さない（「用途」の設計思想に一部反する例外として承知の上での裁定）。他アイテムでは固定値用途は作成不可。
  - **インポート時の自動整形（2026-07-04）**: エキストラ直下に一般技能が作られる際（辞典インポート・ドロップ等の全経路）、元データの「判定」等の**固定値以外の用途を自動削除**し、固定値用途が無ければ**自動追加**（初期値 10）。インポート直後からエキストラの技能は固定値判定のみを持つ。
  - **チャット表示（2026-07-04）**: 通常の判定結果カード（check-result.hbs）の固定値分岐で描画し**レイアウトを統一**。ヘッダー＝技能名＋「技能判定」タグ、カード行はカードを引かないためバッジ「固定値」のみ、計算内訳は達成値の合計行のみ。flags は checkResult 互換（対決読み取りから通常判定と同様に扱える）。

| カード | 判定値 | 備考 |
|---|---|---|

### Aの「達成値21固定」

- 選択した場合、達成値はちょうど21で確定
- 能力値・報酬点・修正値は一切加算されない（完全固定）
- 自動成功ではない（目標値が21を超えることもある）
- **バフもデバフも無視した完全固定（2026-07-15 ユーザー確定）**: 加算要素（報酬点・能力値・判定バフ AE `check.*`・判定ボーナス・状況修正）は `calcSkillCheck` の FIXED_21 分岐が **21 をそのまま返す**ことで engine 段階から無視。さらに**判定確定後の事後修正（用途「判定を修正」＝通常経路）も 21固定では無効**（`_applyCheckModify` が `checkF.result.fixedAt21` でブロック）。**GM メニュー「達成値を修正（手動）」＝管理者権限の最終裁定だけは通す**（バフ/デバフの範疇でないため・`manual` 経路は非ブロック）。再判定は「修正」でなく判定のやり直しのため対象外（別のカードを出せば 21固定でなくなる）。

### Jokerの使い方

- スートと数値の両方を自由に宣言して使用
- 例:「♠9として使う」「♥Aとして使う」など

### 切り札（Trump）の使い方

1. 切り札を消費することを宣言する
2. 手札から好きな1枚を選び、Jokerとして扱う（スート・値を自由宣言）
3. 消費した切り札はそのシーンのシーンカードになる（シーンの雰囲気を塗り替える）

## カードの出し方

- **基本**: 手札から選んで出す
- **山札判定**: 山札から1枚引いてそのカードを使う（絵札が出るとファンブル）

## 手札補充ルール

- 手札からカードを出した直後、**必ず手札上限まで補充する**（山札から自動ドロー）。
- 補充タイミング: カードのプレイ直後（報酬点入力・結果投稿より前）。
- 山札が不足している場合は引ける枚数だけ引く（不足しても処理は中断しない）。
- 山札判定では手札を消費しないため自動補充は行われない。

## 自動失敗の条件

| 条件 | 判定種別 | 備考 |
|---|---|---|
| 使用できないスートのカードを出した | 両方 | **判定不成立による失敗**。判定が成立しないため達成値は 0 になる。起動（カードをプレイする操作）自体は拒否しない—カードは捨て札へ移動し、「判定不成立」として投稿される |
| 山札判定で絵札（J/Q/K）が出た | 両方 | ファンブル（致命的失敗）。RL 裁量でペナルティあり |

### 判定そのものはブロックしない（2026-08-15 ユーザー確定）

**「このゲームで『判定そのものがブロックされる場面』はほぼ（ひょっとしたら全く）存在しません。どの参加者にも平等に『判定を失敗する権利』があります。そのことによって手札を入れ替えていくからです」**（ユーザー verbatim）。

- 判定できない状況は「起動のブロック」ではなく**強制失敗**（判定は通常どおり行われ、結果が達成値にかかわらず必ず失敗になる）で表す。最初の適用は登場判定の「登場：不可」とサンクチュアリの危険値装備（→ [Appearance_Check.md](Appearance_Check.md)）。
- 実装は判定フローの `forcedFailure`: 達成値・内訳は通常どおり算出し成否だけを失敗に固定する。結果カードの成否バナーに理由を表示し、**再判定・事後修正でも成功に転じない**。
- 経緯: 従来実装は「登場：不可」で登場判定ボタンを警告でブロックしていた（2026-08-09 の「登場判定が不可」を Code が起動不可と符号化していた）。2026-08-15 に上記原則が示され、強制失敗へ是正。

## 判定の成立（一般定義・2026-07-17 ユーザー確定）

**判定の成立とは「ファンブル/スート不一致でなければ成立（勝敗は問わない）」**（ユーザー verbatim。「パリーがどうとかリアクションがどうとかは関係ありません」）。**判定全般の一般概念**であり、特定メカニクス固有の規約ではない——「成立していれば効く」系のルール（パリーの受け値＝成立なら敗北でも加算・カバーの成立・社会ダメージの報酬点軽減の起動条件など）は、すべてこの一般定義を参照する（各所で個別に定義し直さない）。

- 経緯: Code が社会ダメージの報酬点軽減の設計時に「パリー受け値と同じ定義で良いか」と**メカニクス固有の定義であるかのように問い**、一般概念であると訂正された（2026-07-17）。

## 能力値の実効値

判定で加算する能力値は、キャストシート閲覧モードに表示される全修正込みの実効値：

```
totalValue = growth + Σ(style.value × styleLevel) + mod + effectMod + abilityOutfitMod
```

## 差分値（2026-07-08 確定・2026-07-09 訂正・フェーズ12）

- **算出は判定の基本機能**: 攻撃に限らず、目標値を持つすべての判定が対象（FS 進行判定なども）。
- **算出タイミング（2026-07-09 ユーザー訂正）**: 差分値の算出は判定フロー上、**成否・勝敗が決定した後に「勝利した場合にのみ」**行われる。`差分値 = 達成値 − 目標値`。**失敗・敗北時に差分値は算出されない**（マイナスの差分値は存在しない＝checkResult では null。当初 Code は常時算出・失敗時は負値としていたが誤り）。目標値のない判定も null。
- **目標値の3モード**: ①固定値 ②対象の制御値（出したカードのスートに対応・カード確定後に解決） ③対決（相手のリアクション判定の達成値と比べる）。どのモードでも解決後に差分値を算出。
  - **③対決は受動有利（2026-07-10 ユーザー確定）**: 相手の達成値は**固定目標値ではなく対決相手の値**。攻撃（能動）側は相手を**上回れば**勝利し、**同値はリアクション（受動）側の勝利＝攻撃回避**（`達成値 > 相手達成値` で命中。`≥` ではない＝トーキョーN◎VA の対決は受動有利の原則）。実装 `resolveOpposed`（`attack-flow-logic.mjs`）。①固定値・②制御値は目標値モードのため従来どおり `達成値 ≥ 目標値` で成功。
- **表示規約**: **目標値があれば判定の種類を問わず必ず差分値を表示**する。表示の有無を決めるのは目標値の有無だけで、判定の種類（攻撃かどうか等）は関与しない（ユーザー確定）。※失敗時は差分値そのものが算出されないため表示もない。
- **式からの参照**: 式評価ヘルパー（Roll のダイスなし決定的評価）で `@diff`（差分値）・`@achievement`（達成値）を参照できる（例: ダメージ式 `2 + @diff`）。数値・算術式・参照キーは機械適用、評価不能な自由文は表示のみ。

## 技能の組み合わせ（確定 2026-06-15、修正 2026-06-17）

### 基本ルール

- 組み合わせの基準となる技能を**ベース技能**と呼ぶ（`skill-base.mjs` の `isAction: BooleanField` で識別）
- **アクション技能は必ずベース技能になる**（組み合わせにアクション技能が含まれる場合）
- 非アクション技能（一般技能・スタイル技能）もベース技能になりうる（アクション技能が含まれない組み合わせでは非アクション技能がベース）
- **アクション技能同士の組み合わせは不可**（ベースは1つのみ）
- 「組み合わせにはアクション技能が必要」は**誤り**（誤解しやすいが、ベース技能になれるだけでアクション技能は必須ではない）
- 組み合わせ可能な技能数: ベース技能を含めて「ベース技能のレベル + 1」個まで
- 一般技能・スタイル技能の区別なく組み合わせ可能

### 組み合わせの条件（両方を満たすこと）

1. **スートの共通部分が存在する**: 組み合わせる全技能で共通して使えるスートが1つ以上必要
   → 使用可能スートは各技能の suits の**積集合**（広がるのではなく狭まることが多い）
2. **タイミングが同じ**: 組み合わせる全技能のタイミングが一致する必要がある

### 組み合わせ後の対象

対象はコンボ成立時に**優先度順**で自動解決される（組み合わせの前提条件ではない）。

優先度（高 → 低）: 自身 ＞ 単体※（単体かつ変更不可）＞ チーム ＞ シーン（選択） ＞ シーン ＞ 範囲（選択） ＞ 範囲 ＞ 単体

### 組み合わせ後の射程（確定 2026-06-20）

射程もコンボ成立時に**優先度順**で自動解決される。

優先度（高 → 低）: **至近※ ＞ 武器 ＞ 超遠 ＞ 遠 ＞ 中 ＞ 近 ＞ 至近**

- 「※」は変更不可（isFixedRange）を表す。
- **変更不可（※）の射程が複数組み合わさる場合は、その中で最も短い射程を優先する**（物理的な近さ: 至近 < 近 < 中 < 遠 < 超遠）。
- **射程「武器」の幅（2026-07-16）**: 武器の射程は {最低, 最長} の幅を持つ（「近～遠」等）ため、「武器」へ解決した射程は幅のまま用途に保存する（`rangeMax`・単一値に潰すと下限が読めなくなる＝ユーザー指摘）。複数武器は幅の**交差**（下限=各下限の最長・上限=各実効射程の最短=従来の「複数は最短」と同値）、交差が成立しない組み合わせは従来どおり最短実効の単点。※交差ルールはユーザーの明示裁定ではなく **Code 提案の採用**（2026-07-16 計画承認に含めて実装）——異なる裁定が出たら是正する。

### 発動パラメータの「解説参照」「その他」（KI-033・2026-07-19 ユーザー裁定＝完全廃止）

- **用途において「解説参照」は不自然**（用途は解説の実装そのものなので自己参照になる）。親データ（技能固有値）が「解説参照」の場合、用途側では「その他」へ自動解決する（対象欄に限らず全欄＝対象・射程・目標値・タイミング。対決欄は用途側に解説参照が存在しないため対象外）。
- 自動入力の優先度では「解説参照」「その他」を**最下位のフォールバック**として扱う（Code 設計・2026-07-19 承認）: 有効値が1つでもあればそちらが勝ち、有効値が無くそれらだけなら「その他」を書き込む（親が「その他」なら自由記入欄も複写・「解説参照」なら空）。上記の対象/射程優先度表（ルール由来）自体は不変。
- **用途シートの選択肢からも「解説参照」を撤去**（技能シート側は原文どおり残す）。保存済みの旧値はアクターへのインポート整備で「その他」へ冪等正規化し、シート表示でも「その他」として扱う。

### 組み合わせのメリット

複数技能に対するボーナス修正を1つの判定に集約できる。
例: 射撃判定 +2・知覚判定 +3 を持つキャラが射撃×知覚で組み合わせ判定 → 達成値 +5

### どの技能を組み合わせるかの設定

**用途（usage）ドキュメントで事前設定**し、その用途から判定を起動する。
設定 UI: アクターが所持するスキルアイテムのドロップダウンで選択（ID 参照）。

### スタイル技能の「技能」パラメータ（comboSkill）

`style-skill.mjs` の `comboSkill: ArrayField({ value, name, isMandatory })` が実装済み。

- 選択肢に**「宣言」（`declaration`）**を含む（**2026-07-14 復元**＝ルールブックの「技能：宣言」表記。本リポジトリの git 履歴の初期時点から欠落していたことをユーザー指摘で発見。連鎖解決では `skillName` 以外の値と同じ扱い＝表記のみで自動化なし）
- 指定技能との組み合わせが必須のスタイル技能がある（`isMandatory: true`）
- 指定技能がアクション技能でなくても、このスタイル技能との組み合わせは可能（特例）
- さらに別の技能を加えたい場合はアクション技能を組み合わせの中に含める必要がある
- スタイル技能でアクション技能のものはベース技能として通常通り使える

### スタイル技能が目標値を内包する場合

- `targetValue` フィールド（`{ value, targetValueNumber, targetValueOther }`）で定義済み
- 組み合わせ判定では**最も高い目標値**を採用する
- 対決判定になった場合: 対決相手の達成値と比べる（**受動有利＝上回りで勝利・同値は受動側勝利**。上記「差分値」③参照）
- **目標値が「制御値」のスタイル技能**: `targetValue.value = "control"` 相当
  → 実際に出たカードのスートが確定するまで目標値が決まらない
  → 例: ♠を出した → 対象の理性の制御値が目標値になる

## 制御判定（確定 2026-06-15）

### 概要

- **下方判定**: 出したカードの値が制御値以下なら成功
- RL 主導の宣言、またはキャストシートの制御値クリックで起動
- **状況修正（手動・2026-07-14 ユーザー確定）**: 制御判定では状況修正は**制御値（成功条件）へ加算**する（CoC で KP が「+10% で判定して良い」と言うのと同じ想定＝正で緩和・負で厳格化。`calcControlCheck` の `manualMod`・内訳に「修正（手動）」行）

### カード値

- 2〜10: 数字通り
- 絵札（J/Q/K）: 10
- A: **11**（21固定オプションは使用不可）
- Joker: ワイルドカード（好きな値を宣言）

### 使用する制御値

- 出したカードの**スートに対応した制御値**（技能判定の能力値と同じ仕組み）
- 例: ♠のカード → 理性の制御値実効値（`totalControl`）が基準値

コード上: `attributeField()` に `control` / `totalControl` 実装済み。

## 使用回数の消費（確定 2026-06-20）

技能には使用回数の制限（`uses.isLimit` / `uses.spent` / `uses.max` / `uses.type`）がありうる（スタイル技能・アウトフィットが保持。一般技能は持たない）。

- **データ表現は D&D 方式の「消費済み（spent）」**（2026-06-20 変更）。`spent` が消費済み回数、**残り = max − spent**。シートでは最大値だけ設定すれば残りは自動算出され、消費済みだけが増えていく（旧 `value`=残り回数から移行。`migrateData` で `spent = max − value`）。
- **消費は判定（用途）の起動に紐づく**。回復・リセット（カット/シーン/アクト境界）はフェーズ15 の領分で、本ルールは**消費のみ**を扱う。
- 用途を起動した判定では、**参加技能（ベース技能＋組み合わせ技能）**のうち使用回数制限を持つものを各 −1 消費する。組み合わせ技能は別アイテムのため**遠隔消費**となる（他技能の用途から使われた技能も消費される）。
- これは Roadmap フェーズ15 の「行動回数制限は自動化しない」（＝ターンごとの行動回数）とは別物。技能個別の使用回数の消費は本ルールで自動化する。
- **0回時の挙動**: 原則ブロック。判定起動時に D&D 方式の「使用回数の消費」ダイアログを表示し、消費チェック済みで残り0の技能があれば起動不可。チェックを外せばその技能を消費せず判定できる。
- 消費の確定はダイアログ（起動時）、実際の減算は**判定の実行時**（カードをプレイした時点）。ダイアログ後にカード選択をキャンセルした場合は消費されない。

## 対決の解釈（是正 2026-07-17。旧「確定 2026-06-20」を全面差し替え）

「対決」欄（`confrontation`）の解釈。**旧解釈「無印の技能名は付与・例示であり拘束しない」は誤りとして撤回**（2026-07-17 ユーザー裁定）。一般則と細則の取り違えが原因——「物理攻撃には〈白兵〉によるパリーと〈回避〉によるドッジが行える」の方が細則であり、その実体は基幹一般技能の対決欄（〈白兵〉〈射撃〉のデフォルト＝「対決:ドッジ、パリー」）にある。

- **対決欄は拘束リスト（一般則）**: ※がなくても、列挙された手段・技能によってしかリアクションできない。
  - **「技能名」（無印）**: リアクションのコンボに、列挙のうち**どれか1つが含まれていれば**よい。
  - **「技能名※」**: その技能を**必ず**コンボに含める（従来解釈から変更なし。単体使用も「組み合わせ」に含むため単体でも当該技能を含む形を指す）。
  - **「手段」行＝リアクション用途タイプの許可**（2026-07-17 タイプ再編で一般化）: ドッジ／パリー／リアクション（精神攻撃）／リアクション（社会攻撃）／リアクション（移動妨害）等。どの技能でその手段を実行できるかは**その用途タイプを持つ技能**（レベル1以上で所持）で決まる。〈電脳〉ドッジ付与技能は「ドッジ用途を持つスタイル技能」であり、対決欄に〈電脳〉が載っている必要はそもそもない（旧解釈の根拠は「手段の許可」と「手段を実行する技能」の混同だった）。**〈自我〉以外で精神攻撃にリアクションする技能も実在**し（ユーザー確認 2026-07-17）、技能名〈自我〉を既定にする形では対応できない——手段行「リアクション（精神攻撃）」なら該当用途を持つ任意の技能が応じられる。
- **組み合わせ判定の対決欄＝構成技能の対決欄の合算（和集合・重複は吸収）**。スタイル技能の「対決:〈回避〉」が〈白兵〉（ドッジ、パリー）と組み合わさっても、既にあるドッジに吸収されるだけでパリーは消えない（旧解釈の懸念はこの合算の見落とし）。精神・社会も同型。
  - **吸収の判定は「既定技能」でなく技能の能力で行う**（2026-07-17 ユーザー裁定・当初「ロール」→タイプ再編で「該当用途タイプの所持」に読み替え）: 合算先に手段行（ドッジ等）が既にあることを確認し、追加しようとする技能名行の技能がその手段の用途タイプを持っていればスキップする。〈回避〉に限らず、同条件の技能はすべて同様にスキップされる。
- **対決判定の判別**: 用途の対決欄に「-」「なし」以外の行が1つでもあれば、その判定は**対決判定**として処理する（「不可」は対決判定だがリアクション不能）。従来の「役割検出でチャットカードの形を決める」方式は廃止（2026-07-17 ユーザー指示）。攻撃タイプの用途には系統既定（物理→ドッジ＋パリー／精神→リアクション（精神攻撃）／社会→リアクション（社会攻撃））が自動で敷かれる——**全て enum 値であり、技能名・辞典キーのハードコードは不要**。
- **一般技能自体は対決欄データを持たない**: 一般技能には対決しない使用も想定されるため、対決欄は**用途で手入力**する（generalSkill DataModel に対決欄は追加しない。辞典にも対決情報なし）。
- **「既定技能」システムは完全廃止**（2026-07-17 ユーザー裁定）: 手段→技能の既定対応（`REACTION_DEFAULT_SKILL`: ドッジ=回避・パリー=白兵・精神=自我・社会=信用）をハードコードしない。実行技能の解決は**リアクション用途タイプの所持**と対決欄の拘束による（リアクション技能選択の既定初期選択も廃止）。`skillRoles`（役割フラグ）と正準名ブリッジも用途タイプへの一回限りの移行後に廃止する。
- **対決の特殊処理はヴィークル操縦時のみ（リアクター側状態由来）**: ヴィークルを操縦しているキャラクターに対する判定は、そのキャラクターについて対決が自動的に**「〈操縦〉※」**になる（アクション側でなくリアクション側の状態で決まる唯一の特例。従来の「搭乗中は回避→操縦へハード上書き」機構を置き換える）。
- **用途の対決欄の選択肢**: 「-」「技能名」「技能名※」「なし」「不可」＋**手段行**（ドッジ／パリー／リアクション（精神攻撃）／リアクション（社会攻撃）／リアクション（移動妨害）等・リアクション用途タイプと1対1）。スタイル技能の対決欄とは異なり解説参照/その他が無い。対決不可は行「不可」へ一本化し、`usage.isUnopposable` トグルは廃止（2026-07-17 ユーザー裁定）。
- **自動入力（参加技能から）**: 用途の既存行を保持したまま、参加技能（スタイル技能）の対決行を追記合算する（完全一致の重複と上記吸収はスキップ）。※置き換えでなく追記なのは Code 設計提案——一般技能が対決データを持たないため、置き換えだと手入力した手段行が消えるため。
- **対決判定カード＝攻撃判定カードの一般化**（2026-07-17 ユーザー裁定）: 攻撃判定のチャットカードを今後「対決判定カード」として一般化し、攻撃でしか必要のない項目（武器・ダメージ関連等）のみ攻撃時に随時表示する。
- **リアクション資格はクリック時点で弾く**（2026-07-17 ユーザー裁定）: 「不可」の場合に限らず、**対決可能な技能を所持していない（レベル1以上で持っていない）**リアクターは、リアクションカードの「リアクションしない」**以外**のボタン押下時点で弾く。資格はボタン（手段/技能名行）ごとに判定する。導線自体は隠さない（対決不可無視技能の存在があるため押下時判定になる＝Code 理解）。
- **「対決不可にもリアクション可」フラグを新設**（2026-07-17 ユーザー裁定）: そのような技能が存在するため。当該技能は「対決:不可」を無視できるが、**下地の対決拘束は受ける**——その対決判定のリアクションにそもそも使用できない技能なら、不可を無視できてもリアクションはできない。
- **「対決:不可」でも下地の対決行を保存する**（2026-07-17 ユーザー裁定）: 不可は大抵単一技能の効果で生じるため、不可が無視・無効化された場合に備え「もし不可でなければどの技能で対決可能なのか」を落とさず保存する。＝不可行はマスクとして下地行（技能名/ドッジ/パリー等）と並存し、自動入力・合算でも下地行を除去しない。
- **実装済み（2026-07-17・本体 `238d775`）**: 対決欄の編集セクション（usage.confrontation・辞典カスケード）・対決判定カード一般化（旧攻撃カード=attackCheck フラグを流用・攻撃専用項目は isAttack で条件表示）・クリック時資格ゲート（selectReactionSkill）・対決不可無視フラグ（usage.ignoresUnopposable）・ヴィークル特例（〈操縦〉※・不可マスクは残す=Code 設計）。対象なしの対決は対決判定カード上の**オープンリアクション**（先着解決・「リアクションしない」=実行者/RL が確定・リアクション側勝利で判定全体が失敗）。対決欄が空の攻撃は制御値で即確定（リアクション導線なし）。既存の攻撃想定用途が対決欄空で「非対決」になる移行は許容済み（フォールバック分岐は作らない）。純ロジックは confrontation-logic.mjs / usage-types.mjs（テスト付き）。

- 神業（`miracle`）は用途タイプを新設せず既存の用途の器で表す。神業であることは**用途の親アイテムの型から導く印**で運ぶ（フェーズ17-1・2026-09-03 確定。旧「当面 declaration に統合・専用システム分離は将来検討」の結論）。用途が0件でも使用回数を消費して神業カードが出る（→ [Miracle_Rules.md](Miracle_Rules.md)「神業の位置づけ」）
- タイプは作成時固定（UI 上で切り替え不可）
- `timing.value = "blank"` / `target = "blank"` は「指定なし」= **どのタイミング・対象とも組み合わせ可能**（自由）

### 信用判定のカードなし特例

ルールブックに「〈信用〉はカードを出さなくても判定できる。達成値 = 外界 + 報酬点」という記述がある。

**解釈・採用（2026-06-20 裁定）**: この特例は**購入判定に限ったルール**として扱う。〈信用〉を使う一般の技能判定では通常通りカードを出す。
（※当初は「〈信用〉を使うすべての判定に適用」と読む案もあったが、適用範囲を購入判定に限定する裁定に確定した。）

**実装方針**: フェーズ8 の汎用判定フローには特例分岐を設けない。購入判定（辞典ブラウザ経由＝フェーズ16・旧17）の実装時に、購入フロー内でカードなし達成値計算（外界 + 報酬点）を扱う。判定種別「購入判定」は [Check_System.md](../Game_Mechanics/Check_System.md) の通り辞典ブラウザ後送り。

## 代用判定（2026-07-09 ユーザー言語化）

技能が指定されて判定する場合（判定要求・FS の進行判定/支援判定の技能指定・情報収集判定など）、**要求されたのとは別の技能で任意に代用判定が行える**。これにより技能指定の強制力を持たせつつ、フレキシブルに自由判定ができる。

- **ペナルティ修正はある可能性があるが、都度判定するユーザーが手入力する形式**（システムは修正を自動で課さない。可否の裁定は卓）。
- **能力値判定を技能判定で代用したり、その逆はあり得ない**（D&D で言えば「セーヴィング・スローを技能判定で代用する」ようなもの＝ユーザー例え）。代用は技能判定の内側でのみ成立する。
- 実装（2026-07-09・本体 `2430680`）: 判定要求の「判定する」で指定技能所持時は「指定技能で判定/代用判定」を選択。未所持時のハードブロックを廃止し代用判定を提示。代用時は技能選択+手動修正入力（calcSkillCheck の manualMod・FUMBLE/21固定に影響しない）。結果カードに「代用」バッジ+指定技能行+修正（手動）行、要求カードのライブ結果にも「代用:〈技能名〉」を明示。
- **コンボ用途の候補列挙（KI-025・2026-07-19 実装・本体 `af12d7b`→UI 二段階化 `5b5c8ad`）**: 指定技能を参加技能（ベース/組み合わせ）に含む**他アイテムの用途**は、代用判定ではなく**要求への正当な応答**として候補列挙される（2026-07-17 ユーザー指摘の実装。組み合わせの可否はユーザー/RL が決める）。UI は二段階（同日ユーザー指示）: 第1段=「〈技能名〉で判定／代用判定」・第2段=**用途名のプルダウン**（指定技能自身の用途+コンボ候補の統合。1 つだけなら自動起動・0 は警告して中止）。起動は唯一の起動関数へ用途 ID 直接指定＝判定ボーナス・適用効果・再判定可能等の用途固有の効果が乗る。**判定要求から起動できる用途は「判定」タイプに限定**（2026-07-19 ユーザー裁定・本体 `fa8d40a`。指定技能自身・コンボ候補の両方に適用——リアクション・移動等の行動種別タイプは各自のフローから起動するもの。当初の Code 設計「通常判定へ流れないフローだけ除外」を置き換え。判定タイプ内でも固定値・NPC取得・バフ宣言フラグは要求カードに結果を返せないため除外のまま）。

## 再判定（2026-07-11 ユーザー確定・2026-07-14 置き換え着地に再設計）

**カードを出し直して判定値を再決定できる**。再判定は**特定技能の能力で可能になる**もの。

- **アンロック＝用途の「再判定可能」（`allowRecheck`）設定**。ON の用途からの判定では、結果カード／攻撃カードの**達成値の数字がクリック可能**になる（常設の破線装飾・所有者/RL にのみ表示）。クリックすると**元の判定と同じ構成**（技能・スート・目標値・判定ボーナス・攻撃ペイロード等）で判定フローが開き直す。※従来の全幅「再判定」ボタンは**廃止**（2026-07-14＝導線は数字クリック／付与／GMメニューに集約）。
- **着地は置き換え（2026-07-14 ユーザー確定）**: 新しい結果カードは投稿せず、**元のカードの達成値が再判定の結果で置き換わる**。元判定に働いた一回性の増強（持続中の効果・組み合わせた判定以外の要素による増強分）はルール上失われるため、**内訳も新しい判定に働いた構成のみに差し替える**（「再判定」タグを表示・事後修正 `checkMods` もリセット）。目標値つきは成否・差分値を再計算し、判定要求カードも追随する。
- **攻撃の再判定はリアクションをやり直さない（2026-07-14 ユーザー確定）**: 解決済み（リアクション／制御値受けが済んでいる）なら**保存済みの相手値**で成否・差分を再解決する。元がリアクション未実施の失敗（スート不一致／ファンブル）や未解決（pending/open）なら新しい結果で仕切り直す（初回のリアクション機会は生きる）。純関数 `resolveAttackRecheckState`（テスト済）。
- **一度だけ（2026-07-14 ユーザー確定）**: 再判定系は基本的に「1度だけ」の能力のため、**一度置き換えたカードは再判定不可**（`checkRecheck.rechecked`＝数字クリック・付与クリック・GMメニューの全導線を閉じる）。イレギュラーな再々判定が必要な卓裁定は GM の「達成値を修正（手動）」で行う。
- **ダメージ算出後は不可＝タイミング不一致（2026-07-14 ユーザー確定）**: 再判定系の能力のタイミングは大抵「（条件つきで）判定が成功した時」「判定に失敗した時」であり、**ダメージ算出後はタイミングが過ぎているため不可**になる（「巻き戻し禁止」が理由ではない＝警告文もタイミングの趣旨）。
- **判定は全て用途を経由する**ため、用途側の設定で全ケースを表せる（能力値判定は再判定能力の対象でない）。※Code は当初「用途を経ない判定があるから汎用ボタン」と誤認して汎用形で実装した——**一般技能は作成時に check 用途が自動挿入され、技能判定は必ず用途経由**であり誤り（ユーザー指摘で `29ead8f` にて用途設定ゲートに修正）。
- **使用回数は再消費しない**（元判定で消費済み）。**報酬点は「使えるか」だけ引き継ぎ、量は再判定時点の所持から取り直す**（元判定で使った分は減っている）。
- **継続処理を持つ判定も全種対応（2026-07-15 ユーザー確定＝旧「対象外（当面）」を上書き）**: リアクション・治療・回復・controlNegate・NPC取得・移動・カバーの判定もスナップショットを保存し、再判定/事後修正の着地で継続処理を再実行する。再実行ポリシーは種別ごと（リアクション=対決の再解決／治療・回復・controlNegate=失敗→成功の遷移でのみ副作用適用／カバー=成立なら印を付け直す／NPC取得・移動=表示のみ）。**種別と再実行ポリシーの正本は `TnxCheckFlow.CONTINUATIONS` レジストリ**（2026-07-16 一本化＝種別リストが複数箇所に散ってカバーの引き継ぎ漏れが起きたのを是正）。
- 実装（本体 `d409992`→`29ead8f`→`4c9ade1`→2026-07-14 置き換え再設計）: スナップショット常時保存（`_buildRecheckContext`）→ `startRecheck`（`recheckBlockReason` ゲート＝一度だけ/ダメージ算出後 → フロー再入・`recheckMessageId`）→ 完了時 `_applyRecheckReplacement`（結果カード＝テンプレート再レンダリングで本文差し替え・攻撃カード＝`resolveAttackRecheckState`＋本文再構築・非作者は `applyMessagePatch` ソケット委譲＝content 込み。2026-07-16 に旧 checkModify を messagePatch へ一本化）。

### 特殊処理の置き場＝右クリックメニュー（GM のみ・2026-07-14 ユーザー確定）

**判定・ダメージへの特殊処理は、チャットカードの右クリックメニューを正規の置き場として集約する**（表示は GM＝RL のみ）。用途フラグ（再判定を付与／判定を修正／ダメージを修正）のアイテムロールは、**同じ内部機能への例外的な外部アクセス**（クリック待ち経由＝メニューを開く必要はない）。「再判定可能」のプレイヤー入口は達成値の数字クリック。今後この種の機能を追加する際もまずメニューに載せる。

- **再判定（この判定をやり直す）**: スナップショット持ち・未再判定・ダメージ未算出のカードに表示。素の再判定（組み合わせなし・置き換え着地）。
- **達成値を修正（手動）**: スナップショット持ちのカードに表示。**加減算（既定）か上書き（チェックボックス・2026-07-14 ユーザー確定）**で入力し「事後修正（手動修正）」行として適用（上書きは内部で差分に正規化＝既存の合算機構に乗せ、台帳は「→N」表記）。**処理が壊れた時の卓の最終裁定ツールのため制限しない**（ダメージ算出後も可）。継続処理系（移動・治療等＝スナップショットなし）は対象外＝達成値だけ書き換えると適用済みの帰結と乖離するため。
- **ダメージを修正（手動）**: ダメージカードに表示。**加減算（既定）か上書き（チェックボックス＝入力値をそのまま新しい攻撃側合計に・台帳は「→N」表記）**で入力し「手動修正」行として合算（用途経由の modifyDamage と同じ着地）。**達成値の手動修正と同じ最終裁定ツールのため適用済みでも制限しない**（2026-07-14 ユーザー確定＝適用済みの実ダメージは巻き戻さない・台帳の記録訂正。用途経由の modifyDamage は従来どおり「算出後〜適用前」）。
- **ダメージ処理をリセット**: `damageRolled` 済みの攻撃カードに表示。フラグを戻して**「ダメージカードを出す」ボタンを復活**させ、算出をやり直せる（2026-07-14 ユーザー確定）。出済みのダメージカードはチャットに残る（整理は手動削除）。リセット後はタイミング系ゲート（再判定・事後修正のダメージ算出後不可）も自然に再び開く（処理を無かったことにする＝タイミングが戻る）。

### 再判定の付与（grantRecheck・2026-07-11 ユーザー確定）

「判定を失敗した時にその技能を組み合わせて同じ判定をやり直す」系の、**他の判定に事後的に再判定を与える能力**の表現。

- **用途の判定モード（ラジオ・通常/再判定を付与/判定を修正＝2026-07-11 排他ラジオ化）で「再判定を付与」（`grantRecheck`）を選んだ** check 用途は、**使用しても判定を行わず**「達成値クリック待ち」モードに入る（もう一度使用するとキャンセル）。「再判定可能」チェックは通常モードでのみ表示（判定を行う用途の性質のため）。
- モード中は**結果カードの達成値がクリック可能**（破線ハイライト表示）になり、クリックすると**その判定に起動技能（付与用途の親技能）を組み合わせた状態で再判定が起動**する——技能が skillIds に加わるためスート積が再計算され、その技能の判定バフ（`check.*`）も判定時に自然に効く。共通スートが無ければ警告して中止。
- **宣言用途でも設定できる（2026-07-13 ユーザー確定）＝素の再判定権のみの事後付与**: 宣言の〈判定〉fieldset の「再判定を付与」チェックボックス（判定を修正等と独立・排他にしない）。**宣言は判定でない＝参加技能が無いため、組み合わせを行わず**、達成値クリックで**元の構成のまま**再判定が起動する（allowRecheck の数字クリックと同じ再実行。共通スート検査も発生しない）。
- **発動条件（失敗時のみ・山札判定のみ等）は自動強制しない**（卓裁定＝効果を自動化しない現行原則。「山札のみ」等の制限の機械的ブロックはユーザー裁定で不採用）。
- 付与用途の**消費（consumeTargets）はプランを持ち回り、再判定の実行時に適用**（通常の check 用途と同じ「判定実行時に消費」の意味論）。
- **着地・一度だけ・タイミング不可は再判定本体と共通**（2026-07-14）: 付与による再判定も置き換え着地で `rechecked` が立つ＝一度だけを消費する。クリック待ち中に対象外のカード（再判定済み／ダメージ算出後）をクリックした場合は**モードを維持したまま警告**（別のカードを選び直せる）。
- 実装（本体 `4c9ade1`→`dd15abe` で汎用化）: `TnxCheckFlow.startAchievementAction("recheck", …)`（モード開始・body クラスで達成値をハイライト）→ 達成値クリック（`_onGrantAchievementClick`）→ `startRecheck(message, { mergeSkill, consumeUses })`＝置き換え着地。スナップショット常時保存が前提。組み合わせの有無はクリック待ち状態の `merge`（check 用途=true・宣言用途=false→`mergeSkill: null`）で持ち回る（2026-07-13）。

### 判定の事後修正（modifyCheck・2026-07-11 ユーザー確定）

**事後的に判定へボーナス/ペナルティを与える能力**の表現。導線は再判定の付与と同じ「技能をクリック→達成値をクリック」。

- **用途の「判定を修正」（`modifyCheck`）を ON** にした check 用途は、使用しても判定を行わず「達成値クリック待ち」モードに入る（再使用でキャンセル。再判定の付与と排他＝後から使った方が有効）。
- **宣言（declaration）用途にも設定できる**（バフ宣言・2026-07-12 ユーザー確定）: 判定を伴わないバフ/デバフ能力を宣言用途で表す場合、同じ「判定を修正」＋判定修正（式）を宣言に設定する。挙動は check 用途と同一（クリック待ち→達成値クリックで適用）。**「判定の直前に使用して直後の判定に修正」もこの機構で表す**——クリック待ちは判定フローの実行を跨いで持続するため、先に宣言を使用（消費は先払い）→判定を実行→出た結果カードの達成値をクリック、の順で忠実に再現できる（直前/直後は加算が線形なので結果も同一）。持続バフ（複数回の判定に乗る等）は用途の適用効果（AE・`check.*` キー）が担当＝単発はクリック適用・持続は AE の棲み分け。
- 達成値クリックで**その判定に修正を適用**する。**値＝その用途の「この用途の判定修正値」（`checkBonusSelf`・式）を使用者のデータで評価**（ペナルティは負の式）。**空・評価不能なら手入力ダイアログ**（可変値の能力・とっさの裁定用。**加減算か上書きをチェックボックスで選べる**＝2026-07-14。用途「ダメージを修正」の手入力フォールバックも同様。式は加算のみ）。
- **適用の帰結**（達成値が変われば帰結も変わる、を機械どおりに）:
  - フラグの達成値を更新し、カードに「事後修正（技能名）: +N」「修正後の達成値」をライブ描画（元の内訳は残す＝全行表示）。
  - 目標値つき判定＝成否・差分値を再計算して表示・フラグ更新（差分値は成功時のみ）。
  - 攻撃カード（未解決）＝達成値のみ更新（以後のリアクション対決・制御値受けは新しい値で解決）。攻撃カード（解決済み）＝保存済みの相手値に対して成否・差分を再解決。**ダメージカードを出した後は修正不可**（算出済みダメージの巻き戻しは整合を壊すため＝唯一の強制。※GM メニューの「達成値を修正（手動）」だけは最終裁定ツールとして例外＝2026-07-14）。
  - 判定要求由来なら要求カードの結果表示も追随。
- **再判定との共存（2026-07-11 ユーザー確定）**: 再判定→事後修正は可能。**事後修正→再判定は修正がリセットされる**（再判定はスナップショット＝元の構成から再実行するため。事後修正はスナップショットに含まれない）。
- 消費（consumeTargets）は修正の適用確定時。他者の判定への修正（ペナルティ等）は非作者のためフラグ更新を GM へソケット委譲（`applyMessagePatch`・2026-07-16 に旧 checkModify を messagePatch へ一本化）。
- 実装（本体 `dd15abe`）: クリック待ち機構を `kind: "recheck"|"modify"` に汎用化（`startAchievementAction`）。`_applyCheckModify` が評価→フラグ更新→再計算。内訳はフラグ `checkMods` からライブ描画。

### スートの変更（suitChange）

カードの実効スートを書き換える能力。判定を成立させるための救済ではなく、変更後のスートが使用可能かどうかは通常の判定規則で判定する。

- 用途の「スート変更可能」（`allowSuitChange`）または付与された AE `check.suitChange` が有効なら、通常カードの使用時にスート変更ダイアログを出す。
- ダイアログは全4スートをプルダウンに表示し、元のスートを初期選択にする。成立するスートへの絞り込み・強調・無効化は行わない。
- 「変更」で選択したスートを以降の全ロジックへ流す。変更後のスートが使用不能なら通常どおり判定不成立になる。
- キャンセルまたは閉じる操作では元のスートを維持して通常処理を続行する。
- 実際に別スートへ変更した場合だけ、結果カード/攻撃カードに「スート変更（元→後）」を表示する。
- 制御判定は対象外。ジョーカー/切り札は既存の宣言処理を使用し、変更ダイアログを重ねない。
- AE の持続時間とキーは独立する。`check.suitChange` は値不要のマーカーキーである。

### 用途の目標値の扱い（2026-07-13 ユーザー確定）

目標値の選択肢はデータ（技能固有値）から拾われるもので、**中身は用途で決めるが、データから拾える目標値を無視して良いわけでもない**。入力先は発動タブの目標値設定の**一箇所**（同じ値の入力先を二重化しない＝回復専用の式欄は廃止）。選択肢ごとの扱い:

- **数字**: 特定の目標値が必ず入る＝**そのまま判定の目標値として消費**する。
- **解説参照／その他**: 自由記入欄に**式を入力して任意に目標値を設定できる**（`@system.*`・`@item.*`／`@skill.<識別キー>.*` 等。回復の判定では `@condition.magnitude`＝選択した状態の強度・`@condition.woundValue`＝負傷のダメージ値も参照可）。空・式として評価できない内容は目標値なし＝記入内容の表示のみ（卓裁定）。※2026-07-19（KI-033）: **用途側の「解説参照」は完全廃止**（選択肢からも撤去・「その他」へ自動解決）。式欄は「その他」で使用する（技能シート側の「解説参照」は原文どおり残る）。
- **制御値／達成値**: 既に別メカニクス（無リアクション時の制御値目標・対決）で実現済みのため具体値は引かない。
- **登場目標値**: 登場判定のメカニクス次第だが、判定フローの中で目標値として明示される可能性が高いため同様に具体値は引かない（登場判定実装時に再訪）。

実装: `resolveUsageTargetValue`（usage-target-value.mjs・テスト付き）。

## 数値供給の実装補足（2026-11-21）

ダメージ修正の適用先は技能の `damageBonusCategories` で物理・精神・社会を独立に指定する。`attackMethod`・対象条件・ダメージ種別とは別軸。パリー受け値の技能寄与は既存の成立判定・武器受け値・修正式評価・参照重複選択を通す。通常判定でも参加技能変更から数値を再解決する。リアクションの分類・AE適用条件は変更しない。保存形式と互換性は [Usage_System](../Game_Mechanics/Usage_System.md) の数値供給拡張を参照。
