## KI-001: active-effects-list.hbs の action 名不一致

**概要**
`templates/parts/active-effects-list.hbs` の `data-action` 値と、
`EffectsSheetMixin.activateEffectListListeners()` の `switch` 文が一致しない。

| テンプレート (hbs) | ハンドラ (switch) |
|---|---|
| `createEffect` | `create` |
| `toggleEffect` | `toggle` |
| `editEffect`   | `edit`   |
| `deleteEffect` | `delete` |

**確認済み**: hbs は `data-action="createEffect"` 等を使用。switch は `"create"` 等で分岐。

**該当ファイル・箇所**
- `templates/parts/active-effects-list.hbs` 全行
- `scripts/module/effects-sheet-mixin.mjs:35` (`activateEffectListListeners` の switch 文)

**影響範囲**
シート表示・基本動作。ItemSheet（miracle/generalSkill/styleSkill/organization）で ActiveEffect
の作成・編集・削除・トグルボタンが完全に動作しない。CastSheet は独自のディスパッチ機構
(`_onCreateEffect` 等のインスタンスメソッド) を使うため影響を受けない。

**修正の難易度**: 低

**フェーズ0 で扱うべきか**: Yes

## KI-008: EXP 計算の連鎖更新による競合リスク（設計上の課題）

**概要**
`updateCastExp()` が `ready` フックで登録された `updateItem` / `updateActor` ごとに呼ばれ、
内部で `actor.update()` を行う。`{calcExp: false}` で直接的な再帰は防いでいるが、複数アイテムを
一括更新した場合（例: createEmbeddedDocuments でスキルを一括インポート）、アイテム数分の
`updateCastExp()` が並列に走り、同数の DB 書き込みが競合する可能性がある。

**該当ファイル・箇所**
- `scripts/tnx.mjs:909-917` (ready フック内の EXP 再計算登録)
- `scripts/actor/tnx-cast-sheet.mjs:1424` (`updateCastExp` static メソッド)

**影響範囲**
その他。通常のアイテム単体の更新では問題は発生しない。
初期技能の一括インポート（`setupDefaultSkills`）時に競合が起きる可能性がある。

**修正の難易度**: 高（設計レベルの変更が必要）

**フェーズ0 で扱うべきか**: No
CLAUDE.md の禁止事項「既存の EXP 計算ロジックを書き換える」に該当する。
表出する問題が確認されてから対処する。

**解消（2026-07-19・本体 `659a2df`・ユーザー承認「合流させたほうがきれいならその方が良い」）**:
`updateCastExp` に同一アクター単位の合流を追加——実行中に来た呼び出しは rerun フラグに畳み、
完了後にもう 1 回だけ再実行する（毎回の全量再計算のため最後の 1 回が最新状態を反映）。
計算・書き込みロジックは `_recalcCastExp` へ改名しただけで不変＝「EXP ロジック書き換え禁止」の
枠内。ユーザー言明: 自動インポート（基本技能）では経験点は消費されないため当該タイミングの
値ずれは元々起こり得ず、本是正は並行する同内容 DB 書き込みの排除。詳細は
[Resolved_Issues.md](Resolved_Issues.md) の KI-008。

## KI-011 [解消済み]: ジャーナルディレクトリの「アクトシートを作成」導線が v13 で機能しない

**概要**
v13 で `JournalDirectory` が `DocumentDirectory`(ApplicationV2)ベースに刷新された結果、
旧 `.create-document` セレクタが DOM 上に存在しなくなり、カスタム作成メニューが表示されなかった。
また、調査の結果 `JournalEntry` はサブタイプ(type)を持たないドキュメントであるため、
Actor/Item のような「作成ダイアログでシート種別をドロップダウン選択する」方式は
コアの仕組み上実現できない。

**解消**: 2026-05-24、フェーズ1-1 にて実装・実機確認済み。
- `renderJournalDirectory` フックで `[data-action="createEntry"]` ボタンの直後に
  「アクトシートを作成」ボタンを1つ挿入する方式を採用(フォールバック方式)。
- 「資料を作成」はコア標準の createEntry ボタンに委ね、独自ボタンは1つに簡素化。
- 旧2択ドロップダウンメニュー(`.tnx-create-menu`)は廃止。

**実機確認**: GM でジャーナルサイドバーを開くと「アクトシートを作成」ボタンが表示され、
押下で TnxScenarioSheet が正しく開くことを確認済み。

**なぜ getHeaderControls 方式ではなくフォールバックを採用したか**:
v13 の `ApplicationV2` ヘッダーコントロールに外部コードから `onclick` 相当を注入する
正確な API が一次情報なしには確認できず、動作保証が困難なため。フォールバック方式が
確実に機能する方式として選択。

**現行のボタン設置方式が最終形**:
- `JournalEntry` はサブタイプを持たないためドロップダウン選択は実現不可(コア制約)。
- `JournalEntryPage` のカスタムサブタイプ化でページ単位の型選択は技術的には可能だが、
  documentTypes 登録によりワールドグローバルに有効化され通常ジャーナルのページメニューにも
  混入するため**不採用**。現行のフラグ+独自タブ UI 方式を維持する。
- 詳細は DESIGN_REVIEW.md「アクトシートのページ化検討と不採用」エントリを参照。

**該当ファイル・箇所**
- `scripts/tnx.mjs` の `renderJournalDirectory` フックハンドラ

**対処内容（`css/tnx.css` 座標調整）**:

| セレクタ | 変更前 | 変更後 | 根拠 |
|---|---|---|---|
| `.hud-top-right` `top` | `5px` | `50px` | v13 トップナビ・シーンコントロールを回避 |
| `.hud-top-right` `right` | `310px` | `360px` | サイドバー(~305px)+シーンコントロール(~50px)を回避 |
| `.hud-main-cards` `bottom` | `10px` | `80px` | サイドバー下部/プレイヤーリストを回避 |
| `.hud-main-cards` `right` | `310px` | `360px` | 同上 |
| `.hand-area` `max-width` | `914px` | `680px` | 1280px 幅画面で右UI に届かない範囲(5枚) |

また死にルール3件(`sidebar-collapsed` / `hotbar-is-collapsed` 依存)を削除。

**残存する軽微な課題(機能的支障なし)**:
- 収納時に右サイドバーとのわずかな視覚的近接が残るが、カード操作への支障なし。

**申し送り(フェーズ2 への)**:

  画面解像度への自動追従が実現する。

  - 左上 = TokenActionHUD のデフォルト位置として空けたまま
  - 右側縦一列の三層構造を維持(上=シーン/ニューロ、中段=将来の情報項目エリア予定、下=山札/捨て札)
  - 空き領域のどこかに他 PC 手札の小型表示を将来追加予定

**該当ファイル・箇所**

## KI-027: 攻撃の適用効果が命中・最終ダメージと突き合わされていない

**発見**: 2026-07-18(適用タイミング2種の設計調査中)
**ファイル**: `scripts/module/usage-effects.mjs`(applyUsageEffectsFromMessage / renderUsageEffectButton)、`scripts/module/damage-flow.mjs`(finalizeDamageRoll / ダメージ適用)

**症状**

1. **回避した対象にも付与される**: 複数対象攻撃の部分命中時、ダメージカードの対象は hit のみに絞られる(`state === "hit"`)が、`usageEffects.targets` は絞られず全員へ付与される。単体攻撃は外れるとダメージフロー自体が起きないため表面化しない。
2. **最終適用値 0 でも付与される**: 付与はダメージ量を見ない。2026-07-18 裁定=「1点でもダメージを与えたら適用」の 1 点は完全な最終適用値であり、0 なら適用しないのが正。
3. **ダメージカードを出さない限り付与経路が無い**: 命中が確定してもダメージロールを省略すると効果は適用不能。「命中時点で適用される効果」はダメージカードの有無に依存してはならない。

**影響範囲**
攻撃用途の適用効果全般。

**修正の方向**
適用タイミング2種(2026-07-18 設計・[Combat_Flow.md](../Game_Rules/Combat_Flow.md)「攻撃の適用効果のタイミング2種」)の実装で是正する: 命中時効果=リアクション解決の hit 確定時に対象ごと付与、ダメージ時効果=ダメージ適用時に最終適用値≥1 の対象のみへ付与(対象はダメージカードの命中対象と一致)。

**修正の難易度**: 中(付与の per-target 化＋フロー二股)

**担当フェーズ**: フェーズ12。適用タイミング2種の実装と同一作業。

**ファイル**: `scripts/module/repair-flow.mjs`(useRepair)、`scripts/module/recovery-flow.mjs`(resolveRecoveryPatient・同構造)、`scripts/module/usage-target-plan.mjs`(usageTargetGroup)、`scripts/module/tnx-usage-sheet.mjs`(deriveUsageAutoFill)

**症状**
修理用途が実行できない。対象欄が既定「-」（や「その他」）のままだと対象解決が空を返し、自分（や味方）をターゲットしていても「修理する対象がターゲットされていません」で中止される。警告文言「対象をターゲットしてください」も誤誘導（ターゲットしても動かない）。

**ユーザー裁定（2026-07-19・同日3回の裁定で確定）**
- **対象の自動解決は、基本的に「ターゲットをし忘れたとき」のための機能**である。対象欄の値で「ターゲットできない用途」を恣意的に決めない＝**対象「-」でも実行をブロックしない**（第2裁定の「『-』で対象にとれないのは正しい挙動」は第3裁定でブロック禁止へ更新）。
- 対象「-」＝完全に対象なし。対象「解説参照」「その他」＝**対象が基本ルールの中で解決できない**ことを指す（完全な対象なしではない）。対象「その他」は「**レティクルでターゲットできない対象を対象にとる**」ときのための項目。
- 修理用途は実態としては対象「アウトフィット」であり、キャラクターを対象に取らない。FVTT ではアイテムを直接ターゲットできないため、便宜的にキャラクターのターゲットを要求しているだけ（どのキャラクターの所持品かを指す）。
- 用途において「解説参照」は不自然。対象欄に限らず、**親アイテム側でデータが「解説参照」の場合は「その他」に自動解決するシステムが必要**。
- ※第1裁定にあった「対象『なし』が存在する」は再裁定で訂正（存在しない）。

**修正の方向（Code 提案・未承認）**
① 修理フロー: 対象欄の値で分岐・ブロックしない。ターゲット中のキャラクターがいればそのキャラクター、いなければ自分（し忘れ時の自動解決）の故障アウトフィットを列挙・選択する。「修理する対象がターゲットされていません」警告は撤廃（到達しなくなる）。作成時既定の変更も不要。
② 治療（判定形）の「回復する対象がターゲットされていません」も同じブロック構造のため、同原則（ターゲット中→患者・未ターゲット→自分）で同時に是正する（含めるかは承認事項）。
③ 「解説参照」→「その他」の自動解決: 親データから発動パラメータを写す経路（deriveUsageAutoFill 等）で、対象欄に限らず「解説参照」を「その他」へ写す。現行の自動入力は blank/解説参照/その他を無視して何も写さないため、「参加技能に有効値が無く解説参照/その他だけがある」場合に用途を「その他」とする挙動もここで確定させる。①②とは別作業単位。

**修正の難易度**: 低〜中

**担当フェーズ**: フェーズ12。

**解消（2026-07-19・本体 `e3b7297`）**: ターゲット関連ブロックの全廃（最終裁定=明示ターゲットを「正規ではない」とはじくのは本末転倒・自動解決はし忘れの救済）で是正——`resolveTargetedOrSelf`（ターゲット中→その相手・未ターゲット→自分＝レティクル付与）へ修理・治療/回復の対象解決を一本化し、「〜対象がターゲットされていません」警告2種と妥当性 invalid（「ターゲットが間違っています」）を撤廃。「解説参照」→「その他」の自動解決は KI-033 へ分離。詳細は [Resolved_Issues.md](Resolved_Issues.md) の KI-032。実機確認済み（2026-07-21）。

## KI-050 [解消済み]: 新規に追加したアイテム自身が持つアイテム狙い AE が、その時点で転送されない

- **起票**: 2026-09-02（KI-049 の追跡中に、単発追加の挙動を切り分けて発覚）
- **症状**: 他のアイテムを狙う AE（`item.<識別キー>` / 分類狙い・自動適用オン）を**内包したアイテム**をアクターへ追加しても、その場では転送コピーが作られず**効果が乗らない**。別のアイテムを追加する・効果を開いて保存し直す・装着を変える等の別操作が起きて初めて転送される。
- **再現（隔離 Foundry）**: 対象武器（識別キー `ki048b`）を持つキャストへ、`item.ki048b.system.hide.value` +2 を内包した一般アイテムを単独で追加 → 1.5 秒待っても転送コピー 0・隠匿値は素値のまま。無関係なアイテムを 1 つ追加した直後に転送コピー 1・隠匿値が +2 される。
- **原因**: `createItem` フック（`tnx.mjs`）が `if (it.id === item.id) continue;` で**追加されたアイテム自身を走査から外している**。このフックは「新しいアイテムを**狙われる側**として既存の供給元を実体化し直す」意図で書かれており、新しいアイテムが**供給元側**になる経路が無い。Foundry はアイテムに内包して作成された効果に対して `createActiveEffect` を別途発火しないため、そちらでも拾えない。
- **影響度**: 辞典から「他のアイテムを強化する」品（ドラッグ・サイバーウェア・武器オプション等）をドラッグしたとき、効果が無言で効かない。2026-07-13 の申し送り「既存の効果は一度保存（または OFF→ON）すると転送される」と同じ手間が、**新規追加でも必要**になっている。
- **状態**: **解消済み**（2026-09-02 同日・詳細は [Resolved_Issues.md](Resolved_Issues.md) KI-050）。

## KI-051 [解消済み]: 神業の「母数-1」が効かず多重取得の神業がアイテムごと消える（コンソールエラーはその副作用）

- **起票**: 2026-09-05（チャットカード統一規格の実機確認中に、仕込みでアイテムを削除した際の副産物として発覚）
- **症状**: アクターの所持アイテムを削除すると、ブラウザのコンソールに `Cannot read properties of undefined (reading 'id')` が 1 件出る。スタックは Foundry コア `ServerDatabaseBackend._updateDocuments`（更新対象の文書が見つからないまま `.id` を読む）。**卓の進行に見える影響は無い**（削除自体は成功する）。
- **再現（隔離 Foundry）**: キャストへ神業アイテムを 1 つ作成 → `item.delete()`。削除の直後にエラーが 1 件。カードの投稿・アクター作成では出ない（切り分け済み）。
- **原因（2026-09-05 特定）**: `preDeleteItem` フックが **async** だった。Foundry の pre 系フックは戻り値を**同期**で見るため、async 関数の `return false` は Promise（truthy）になり**削除を止められない**。その結果、
  1. 神業の「母数（uses.max）が2以上なら削除でなく-1（多重取得の1つを外す）」というルールが**まったく機能しておらず、アイテムごと消えていた**（実機で確認: 母数2の神業を削除 → 残らない）。
  2. 止めたつもりで投げた `item.update()` が「もう無い文書」に当たり、サーバが `_updateDocuments` でエラーを返していた（＝コンソールに見えていたもの）。
- **影響度**: 中。コンソールの汚れではなく**ルールの欠落**（同じ神業を複数のスタイルから取得している状態が壊れる）。
- **解消**: 本体 `3bf3c57`。`preDeleteItem` / `preUpdateItem` を同期にし、止める判断を同期で行う（非同期の後始末は IIFE で流す）。母数の判定は純関数 `miracleRemovalUpdate`（テスト+3）。実機で「母数2→残って母数1」「母数1→削除」「コンソールエラー無し」を確認。
- **教訓**: **Foundry の pre 系フックを async にしない**。止める（`return false`）判断は必ず同期で返す。
- **関連**: KI-048〜KI-050（アイテム狙い AE の転送・失効）。当初は AE コピー除去を疑ったが別経路だった。

## KI-056 [解消済み]: ダイアログのキャンセルが取りこぼされ、選択したことにして進む箇所がある

- **起票**: 2026-09-07（神業の治癒「BS・ダメージ以外の不利な効果も解除」の実機確認中に、回復対象の選択ダイアログでキャンセルするとコンソールエラーになったことから発覚）
- **原因**: `DialogV2` は **「コールバックの戻り値 ?? ボタンの action」** で解決する（`client/applications/api/dialog.mjs` の `_onSubmit`＝`(await button?.callback?.(...)) ?? button?.action`）。本システムの多くのダイアログはキャンセルに `callback: () => null` を置いているが、`null ?? "cancel"` ＝ **文字列 "cancel" が返る**。受け側の `if (!picked) return;` は文字列を truthy として通してしまう。
- **既知だった**: `session-state.mjs`（アクト限定アイテムの掃除）に同じ罠の実機発覚メモ（2026-08-14）とガード（`Array.isArray`）がある。`tnx-usage-sheet.mjs` も `Array.isArray` で守っている。**規約として広がっていなかった**のが問題。
- **実害のある箇所（2026-09-07 時点・確認済み）**:
  - `recovery-flow.mjs` 回復対象の選択 → **解消済み**（本コミットで `typeof picked !== "object"` ガード）。旧コードでは「該当すべて」設定のときキャンセルしても**使用回数を消費してカードまで出ていた**（除去は0件）。
  - `modification-flow.mjs` 改造項目の選択（`if (!pick) return;`）→ キャンセルで**判定が始まり**、成功すると `param: undefined` の改造行が書かれる。ドラッグ選択（`if (!drugIds) return;`）も同様に判定へ進む。

  - `condition-edit.mjs` コンディション編集（`if (!result) return;`）→ 文字列を展開して `{0:"c",1:"a",…}` を**フラグに書き込む**。
  - 偶然助かっている例: `appearance-check.mjs`・`repair-flow.mjs`・`modification-flow.mjs` の対象選択・`tnx-rl-request-app.mjs`（後段の `items.get(...)`/`find(...)`/`?.skillId` が undefined になり中止される）。

- **解消**: 2026-09-07（フェーズ18）。→ 詳細は [Resolved_Issues.md](Resolved_Issues.md) KI-056。
