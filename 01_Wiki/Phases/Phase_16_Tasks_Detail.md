# Phase 16: 辞典ブラウザ + 購入・改造判定UI

> ▶ **計画確定 2026-08-30**（旧フェーズ17＝2026-08-30 番号正規化。設計議論 2026-08-30・各裁定の正本は [Purchase_and_Modification](../Game_Rules/Purchase_and_Modification.md)）。実装は設計承認後にサブフェーズ順で着手し、各サブフェーズの詳細仕様は着手前に提示する（14/15 と同運用）。

**辞典ブラウザ自体は購入・改造専用ではなく、それ以外にも用法のある独立した汎用アプリケーションである**（2026-08-30 ユーザー明示）。全辞典パック（スタイル・神業・技能3種・オーガニゼーション・アウトフィット2種・住宅エリア・ライフパス・NPC 等）の参照・検索・取得を第一級で担い、購入判定・改造判定は**ブラウザに乗る連携機能**として実装する。ブラウザを購入・改造の付属物として設計しない。

ルールの正本は [Purchase_and_Modification.md](../Game_Rules/Purchase_and_Modification.md)（購入・改造・分類別改造可能項目・複数分類）・[Check_Rules.md](../Game_Rules/Check_Rules.md)（信用判定カードなし特例＝購入判定限定）・[Outfits.md](../Game_Rules/Outfits.md)（購入値 `buy` ほかパラメータ）・[Scenario_Progress.md](../Game_Rules/Scenario_Progress.md)（舞台裏判定の枠組み）。ブラウザ自体は UI 設計＝本ページと 16-2 詳細仕様が記録先。

## 表示形式（2026-08-30 ユーザー方向づけ）

**狙い**: 本システムは D&D のように資料（ルールブック相当のジャーナル）を同梱することをおそらくしないため、**辞典ブラウザのデータ表示だけでもルールブックの読書体験に近づける**（ユーザー言語化）。

- **スタイル技能・アウトフィット＝ルールブック/サプリメントのデータカード形式を踏襲**（ユーザー指定・スクリーンショット提示 2026-08-30）: 分類見出しカード（分類名＋説明）＋データカードのグリッド。カードは名前ヘッダ＋パラメータ行（スタイル技能: 技能/上限/タイミング/対象/射程/目標値/対決。アウトフィット: 購/隠/攻/受/防/制/射/電制/部位 等の略号行）＋解説文という構成。**ただし完全に同じデザインにはしない**（ユーザー明示「完全に同じデザインにしてしまうのはまずい」＝形式・情報配置の踏襲に留め、視覚意匠は TNX の既存デザイン言語（tnx2.css）で再解釈。装丁・ロゴ等の複製はしない）。
- **一般技能＝D&D 5e 辞典ブラウザ風の縦積みリスト＋α**（ユーザー指定。原作に明確なカード形式が存在しないため）: サイドバーのフィルタ群＋検索・行リスト。「＋α」の中身（TNX 固有の列・フィルタ＝区分・対応分類等）は 16-2 詳細仕様で提示。
- 他パック（スタイル・神業・オーガニゼーション・ライフパス・住宅エリア・NPC 等）の形式は 16-2 詳細仕様で個別に提示して確認する。
- **アクターシートのアイテム・ツールチップ**（ユーザー指定・この機会に新設）: アクターシート上のアイテム群にカーソルオンで、**辞典ブラウザと同じカード型**のツールチップを表示する。カード HTML 部品をブラウザと共通化（ビルダー1つ・HUD シーンカードのチャットカード意匠ツールチップ（14-8）と同じ構成パターン）。所持アイテムのツールチップは**実効値**で表示する（表示は全箇所実効値の規約・辞典ブラウザ側は辞典の素値）。

**含まない（Code 整理・取り込むなら裁定）**

- 常備化（常備化経験点 `preserveExp` による事前購入の自動化）: 申し送りに含まれておらず、EXP 機構は不可侵（§4.3）。導線を作る場合は別途裁定。
- 行動回数・購入回数の制限: 恒久非スコープ（判定はブロックしない原則）。購入判定が舞台裏インスタンスであることはゲートにしない（導線のみ）。
- ドラッグ改造の自動化の深さ: パラメータ修正ではない特殊効果のため、扱い（記帳のみ〜選択 UI）は 16-4 詳細仕様で提示。

## 確定した設計判断（2026-08-30 計画議論）

ユーザー明示裁定と Code 提案採用を区別して記す。

1. **起動＝辞典（コンペンディウム）タブ上部のボタン**（ユーザー明示＝当初からの指示。旧記録「ドロップエリアクリック起動」は Code の誤記録として訂正済み）。
2. **改造の表現形＝専用修正フィールドの新設**（ユーザー裁定・AE 表現案は不採用）。素値（辞典原本値）は保ち、アウトフィットの改造記録を `prepareDerivedData` で実効値に合流させる。改造項目・値・供給元をシート上の専用枠で表示する。
3. **複数分類＝副分類の配列**（Code 提案採用）＋ **チェックボックス展開 UI**（ユーザー指定・verbatim は Purchase_and_Modification）: 1行目右端にチェックボックス（ツールチップ「複数の分類を持つアウトフィット」）→ ON で同形式のプルダウン行が出現・2行目右端は追加ボタン・3行目以降は削除ボタン。チェック状態は副分類の有無から導出する（状態レス・Code 設計）。主分類は置き場所（グループ表示・部位/スロット）の権威のまま。
4. **isCyber は副分類に完全に統合**（ユーザー裁定 verbatim「isCyberは副分類に完全に統合します」）: フィールド廃止・特徴フラグ欄から撤去・主分類サイバーウェア→自動セット機構も撤去。既存データは移行（isCyber=true かつ主分類≠サイバーウェア → 副分類にサイバーウェア追加）。**ユーザー正本データの書き換え＝実装時に明示報告**。
5. **分類判定ヘルパー一本化**（Code 提案採用）: 主分類＋副分類の集合を返す関数1つに集約し、「サイバーウェアか」「分類 X か」を問う全読者——改造可能項目・製作技能対応・部位ホスト照合・「※」表示・電子妨害カウント・修理対応分類・サービス免疫——をヘルパー経由へ統一。**電子妨害は従来 isCyber 横断を数えていなかったため、体内武器等が新たにカウント対象になる挙動変化を含む**（Code 帰結整理・「両方の分類として扱う」原則）。
6. **製作技能の対応分類**（ユーザー裁定）: 一般技能に欄を追加。societyClass と同形＝区分が製作（craft）のときのみ表示。選択肢は大分類＋小分類の混在（**サービスとその配下小分類は除外**）。キー空間は修理対応分類 `repairableCategories` と同一（大分類・小分類キーは全体一意）。
7. **用途 `modifiableParams` の撤去**（Code 提案・読者ゼロ確認済み 2026-08-30）: 改造可能項目は対象の分類から導出するため、用途側の手動リストは廃止する。
8. 改造可能項目の分類別テーブルは**システム定数**としてコード化する（構造的最小限＝§4.1 の範囲。効果文の転記ではない）。

## サブフェーズ

- **16-1 分類基盤**: 副分類フィールド＋展開 UI・分類判定ヘルパー・isCyber 完全統合（データ移行含む・明示報告）・既存読者の付け替え（部位照合／※表示／電子妨害／修理／サービス免疫）・製作技能の対応分類欄・`modifiableParams` 撤去
- **16-2 辞典ブラウザ基幹**: ApplicationV2・辞典タブ上部ボタン起動の**汎用ブラウザ**。全パック横断一覧・**種別別の表示形式**（スタイル技能/アウトフィット＝ルルブ踏襲のカード型グリッド・一般技能＝D&D 風リスト＋α・他は詳細仕様で個別提示）・パック種別ごとのフィルタ（技能=区分/対応分類等・アウトフィット=大分類/小分類/購入値等）・名前検索・参照表示（シートを開く）・ドラッグ取得（キャラクター構築の取得導線）。**カード HTML 部品の共通ビルダー**を切り出し、**アクターシートのアイテム・ツールチップ**（スコープ7）をここで配線する。詳細仕様の提示時に**用法一覧**（購入・改造以外を含む）を出す
- **16-3 購入判定**: ブラウザ→購入フロー。カード判定＝〈信用〉解決→`_activateItemCheck` に TN=購入値を自動供給＋完了継続（登場判定と同型）／カードなし特例＝購入フロー内で 外界実効値＋消費報酬点（汎用判定フローに分岐を作らない＝Check_Rules 実装方針）／購入値が外界点以下は常時入手／成功で辞典から複製付与
- **16-4 改造判定**: コンボ起動・対象アウトフィット選択・分類別項目の提示（＋［レベル］・ヴィークル制御値修正の最大0キャップ・防御力 S/P/I 一括・住宅施設の二択・ドラッグ特殊）・「ー」「解説参照」「購入値ー」の不可判定・専用修正フィールドへの適用＋実効値合流＋シート表示
- **16-5 仕上げ**: ウェット識別キー実値確定・実機確認一括・v0.16.0
