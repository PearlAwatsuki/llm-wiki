# FS判定（フォーカスシステム）実装設計

フェーズ12-5 の設計正本（2026-07-20 ユーザーとの設計セッションで確定）。ルール解釈の正本は [Focus_System.md](../Game_Rules/Focus_System.md)。

本ページは**フェーズ12 で作る基幹**（設定の置き場・起動・進行状態の手動管理）を扱う。実判定の接続（進行判定の実行→進行値の自動加算、支援判定の AR 消費と +1）は**フェーズ13**。

## 設計の経緯（重要）

2026-07-09 に「JournalEntryPage 型 `focusSystem` を新設」する案が**ユーザー未承認のまま承認済みとして誤記録**され、取り消された経緯がある（→ Focus_System.md の注記）。2026-07-20 にユーザーが**一部撤回**し、以下が確定した。

- **FS判定シートは JournalEntryPage 型として新設してよい**。ただし**設定の情報置き場と閲覧用**であり、**進行状態の正本ではない**（2026-07-20 ユーザー明示）。
- 1 ドキュメント＝1 ページ＝1 FS判定。**1 つのジャーナルに複数ページを並べて並行 FS を表す運用は採らない**（2026-07-20 ユーザー明示）。並行して走る FS は正本側（`activeFocusSystems` 配列）で表現する。
- 起動はシーンコントロールから。判定要求 UI を踏襲し、手動設定とシートからの読み込みの両方を可能にする。

## 全体構成

| 層 | 実体 | 役割 |
|---|---|---|
| 設定 | `JournalEntryPage` 型 `focusSystem` ＋ 専用シート | FS の設定を書き溜め、閲覧する。**実行状態は持たない** |
| 正本 | ワールド設定 `activeFocusSystems[]` | **進行中 FS の唯一の正本**（進行値・カット数を含む） |
| 操作・閲覧 | FS判定パネル（シーンコントロールから開く） | 進行値／カットのゲージ操作（RL）・閲覧（全員） |
| 通知 | FS開始カード／結果カード | チャットへの掲示。**状態は持たない**（正本の二重化を避ける） |

### 正本をページに置かない理由

FS はカットをまたいで繰り返し参照・更新される長期状態であり、単発で閉じる判定要求カードとは機能が異なる。チャットカードを正本にすると RL が進行値を動かすたびに過去のカードへ遡る必要があり、並行 FS では更に探しづらい。ワールド設定に置くことで、いつでも同じ場所から参照でき、フェーズ13 でコンバットトラッカーにカット進行が入った際も**正本の引っ越しなしに**トラッカーから読める。

## FS判定シート（`focusSystem` ページ）

`scripts/data/journal/focus-system.mjs` に DataModel を置き、`system.json` の `documentTypes.JournalEntryPage.focusSystem` に宣言する。シートは `DocumentSheetConfig.registerSheet(JournalEntryPage, "tokyo-nova", ...)` で `types: ["focusSystem"]` に登録。作成導線はアクトシート作成ボタンと同型（`focusSystem` ページを 1 枚持つジャーナルを作る）。

| フィールド | 型 | 内容 |
|---|---|---|
| （ページ名） | Document | FS 名。DataModel には持たない |
| `restriction` | String | 制限（参加条件）。自由文・**表示のみで強制しない**（ルール7） |
| `defeatCondition` | Object | 敗北条件（下記・ルール2/16） |
| `defeatEffect` | String | 敗北時の処理（ダメージを受ける等・自由文・表示のみ。ルール17） |
| `targetProgress` | Number | 目標進行値（進行値ゲージの最大値。ルール1） |
| `supportSkillKey` | String | 支援判定の指定技能（識別キー。ルール11） |
| `rows[]` | Array | 進行判定の判定行（下記） |
| `memo` | String | メモ欄 |

### 敗北条件 `defeatCondition`

敗北条件はカット経過とは限らない（ルール16）ため、自由文一本にせず種別を持たせる。

- `type: "cut"` — カット経過。`cutLimit`（敗北カット数）が有効になり、パネルにカットゲージと**残りカット数**を表示する
- `type: "other"` — それ以外。`text`（自由文）を表示し、**カットゲージと残りカット数は出さない**（「残りカット数」はカット条件限定の表現）

### 判定行 `rows[]`

| フィールド | 内容 |
|---|---|
| `threshold` | 進行値＝**切り替えの閾値**（ルール8）。一番上が初期値 |
| `skillKey` | 指定技能（識別キー） |
| `targetValue` | 目標値 |
| `progressMod` | 進行修正（下記） |
| `note` | 備考 |

行は手動並び替え可（TNX 標準）。**有効行の決定は閾値 ≦ 現在進行値 を満たす行のうち閾値が最大の 1 行**（ルール12）。飛ばされた行が無視される挙動（ルール9）はこの定義から自動的に満たされる。

**支援判定に専用の目標値欄は持たない**——ルール5 により支援判定の目標値は進行判定と同じなので、その時点の有効行の `targetValue` を使う。

## 進行修正 `progressMod`

進行修正は固定値のこともあれば、アウトフィットのデータ（例: タップのサイクル数）やアクター側の数値（例: 生命の能力値・制御値に係数をかけた値）を参照することもある（ルール4・2026-07-20 補足）。

`{ source, param, formula }` の 3 要素で表す。

- `source` — `none`（固定値）／`outfit`（アウトフィット）／`actor`（キャラクター）
- `param` — 参照するパラメータ。`source` が `none` 以外のとき、**グループ形式プルダウン 1 本**で選ぶ（`outfit` ならアウトフィット種別ごとの optgroup、`actor` なら能力値／制御値等の optgroup）。技能プルダウンの分類グループ化と同じ形式
- `formula` — 式。`param` の解決値が **`@param`** として入る。係数は式で表現する（`@param * 2`、`floor(@param / 2)`）。`source` が `none` のときは式に数値を書くだけ

**式キーでアイテムを直接指定することはできない**（2026-07-20 ユーザー指摘）——キャラクターがどのタップを装備しているかは FS 側から特定できないため。`outfit` を選んだ場合、**実判定時に判定者の準備済みアイテムから該当種別を探して解決**し、複数該当すれば判定者に選ばせる（解決はフェーズ13。フェーズ12 は保存まで）。

UI の非対称を避けるため、アクター側パラメータも式直書きではなく**プルダウン選択に統一**する（2026-07-20 ユーザー指示）。プルダウンに出す候補は内部キーの生値ではなく表示ラベルとする（種別×パラメータの対応表が必要）。式評価は既存の `evaluateFormula` / `buildFormulaData` を使う（→ [Formula_Reference.md](Formula_Reference.md)）。

## FS判定パネル（進行状態の正本）

ワールド設定 `activeFocusSystems`（scope: world）に進行中 FS の配列を持つ。

```
{
  id,                 // ランダム ID
  sourcePageUuid,     // 読み込み元ページ（手動設定なら null）
  name, restriction, defeatCondition,
  targetProgress, cutLimit, supportSkillKey, rows[],   // 起動時のスナップショット
  progress, cut       // 進行状態
}
```

**スナップショット方式**——起動後にページを編集しても進行中の FS は変わらない。

シーンコントロールの「FS判定」ボタンから開く。判定要求ボタンが GM 限定なのに対し、**こちらは全員に表示**する（プレイヤーが進行状況を参照できるようにするため・2026-07-20 ユーザー指示）。RL は編集可、PL は閲覧のみ。**進行中の FS が無いときは「進行中のFS判定はありません」を表示**する。

進行値・カットは**現在値／最大値のゲージ**で表示し、RL が手動で増減する（2026-07-20 ユーザー確定）。既存の `outfit-slot-gauge` はピップ式で 5〜10 個規模向けのため進行値 30 には合わない。**セレクタを広げず、バー式のゲージ部品を別に起こす**。

進行値ゲージには最大値（目標進行値）・現在値に加えて、**判定行の閾値をマーカーとして刻む**（切り替わりポイントが目で分かる形・2026-07-20 ユーザー指示）。カットゲージは `defeatCondition.type === "cut"` のときのみ表示する。

### 達成・敗北の確定

敗北時にはダメージを受けるなどの処理が入る（ルール17）ため、**敗北を確定する操作が必要**。パネルに「達成」「敗北」の確定ボタンを置き、押すと `activeFocusSystems` から除去して結果カードを投稿する。

**敗北時の処理はシステムが自動化しない**——内容が FS ごとに異なるため。結果カードから「ダメージを与える」導線を置き、RL 任意ダメージ付与（→ [Damage_Rules.md](../Game_Rules/Damage_Rules.md)「RL による任意のダメージ付与」）へ繋ぐ。

## 起動フロー

1. パネルの「新しい FS判定を開始」→ 起動フォーム（判定要求ダイアログの構造を踏襲）
2. 先頭の**読み込み元プルダウン**でワールド内の `focusSystem` ページを選ぶ（所属ジャーナル名の optgroup／「手動設定」）。選択で各欄が自動投入され、そのまま手で直せる
3. 送信 → `activeFocusSystems` に追加し、**FS開始カード**（全体公開）を投稿。カードは名称・制限・敗北条件・判定行・現在の進行値／カットを掲示する**通知**であり、状態は持たない

## 進行判定・支援判定の要求

どちらも単発で閉じる判定なので、**既存の判定要求機構（`checkRequest`）にそのまま乗せる**（機能が一致するため流用してよい箇所）。カードには FS の文脈（どの FS か）を持たせ、13 が結果を受け取れるようにしておく。

| | 技能 | 目標値 | 宛先 |
|---|---|---|---|
| 進行判定 | **有効行**の `skillKey` | 有効行の `targetValue` | メインプロセスを行うキャスト**1名**（ルール14） |
| 支援判定 | `supportSkillKey` | 有効行の `targetValue`（ルール5） | AR の残った参加キャスト**全員**（複数人可・ルール15） |

**参加アクター＝コンバットトラッカーの登録者**（ルール13）。FS 側に参加者リストは持たない。`Combat` / `Combatant` は Foundry コアのドキュメントで **12 の時点でも `game.combat.combatants` を読める**——13 で作るのはトラッカー UI の上書きとプロセス進行であり、参加者という概念自体は既に存在する。Combat が無い場合はワールドのキャストから選ぶフォールバックを置く。

**12 の範囲**（2026-07-20 確定）:

- **支援判定要求は 12 で完成する**。宛先は参加者全員。**AR 残量による絞り込みのみ 13**。
- **進行判定要求も 12 で完成する**。「今が誰のメインプロセスか」の自動判別は 13（TNX のプロセス進行）だが、**宛先を RL が手で選ぶ**形にすれば 12 で機能する（RL は誰の手番か分かっている）。13 で自動判別に差し替えるだけで済み、カード構造も見た目も変わらない。

## 判定要求プリセット（アクトシート「判定要求」タブ）

FS判定と同じ「事前に設定して読み込む」構造を、判定要求にも用意する（2026-07-19〜20 ユーザー提案）。シナリオに記載のある判定要求を事前に書いておき、卓では選ぶだけで起動できるようにする。

アクトシート（`JournalEntry` の flags）に `checkRequests[]` を追加する。

```
{ id, label, checkType, identificationKey, customSkillName,
  validSuits, targetValue, targetValueHidden, description }
```

`label` は RL がつける分かりやすい名前（プレースホルダー＝「判定要求n」）。手動並び替え可。判定要求ダイアログの先頭に読み込み元プルダウンを追加し、選択で各欄を自動投入する。

**対象アクターはプリセットに含めない**（2026-07-20 ユーザー確定）——卓の状況で変わるため起動時に選ぶ。

## 純ロジック（TDD 対象）

- `activeProgressRow(rows, progress)` — 閾値 ≦ 進行値 のうち閾値が最大の 1 行を返す（該当なしは null）
- `resolveProgressMod({ source, param, formula }, data)` — `@param` を注入した式評価
- ゲージのクランプ（0 ≦ 現在値 ≦ 最大値）と閾値マーカーの位置算出
- プリセットの読み込み投入（プリセット → フォーム値への写像）
- 進行/支援判定要求の技能・目標値の決定（有効行からの導出）

## フェーズ13 への申し送り

- 進行判定の実行 → `floor(@diff/10) + 進行修正` の自動加算
- 支援判定の AR 消費と、対象の次の進行判定への +1
- **支援判定要求の宛先を AR 残量で絞り込む**
- **進行判定要求の宛先を「今のメインプロセスのキャスト」で自動判別する**（12 は RL の手動選択）
- `progressMod.source === "outfit"` の実解決（判定者の準備済みアイテムから該当種別を探し、複数なら選択）
- コンバットトラッカーのカット進行と `cut` の連動
