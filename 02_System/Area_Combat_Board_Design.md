# エリア概念戦闘盤面：実現可能性と設計案

作成日: 2026-09-12。対象: TNX 0.17.0 / Foundry VTT 13（system.json: minimum 13、verified 13.351）。
状態: **基本盤面実装・Scene設定への統合済み。実セッション検証待ち**。

## 実装後の確定UI（以下の設計時の記述より優先）

Sceneの「グリッド」タブ末尾へfieldset/legendの「エリア戦闘」セクションを追加する。専用ウィンドウや起動ボタンは撤去した。幅/高さ・行列・原点・枠色/不透明度を同じフォームで編集し、既存の「変更を保存」で標準項目と同じsubmitDataとして保存する。TnxSceneConfigはコアSceneConfigを継承し、grid本文へ追加するためタブ見出しには挿入しない。

有効中はグリッド種別を「グリッドなし」と表示し、種別選択と標準グリッド調整を無効化する。無効にすれば再選択できる。入力中のプレビューはローカルのみで、閉じれば保存済み状態へ戻る。保存済みのareaCombatフラグは継続利用する。

移動段階と距離を表示し、通常ムーブは生身1または実効SF。判定カードから現在の移動段階を参照でき、再判定や妨害の更新に追随する。上限の強制はしない。

検証: 全131ファイル2,906テスト、ESLint、Stylelint通過。コアgridテンプレート（標準フォームヘルパーは代替）と追加テンプレート・実CSSをEdgeで描画し、配置とフォーム/保存ボタン各1つを確認した。実セッションでの保存・移動・同期は未確認。

## 1. 結論と根拠

**実現可能と判断する。** 推奨構成は「FVTT Sceneをグリッドなしにする＋システム独自の大きな矩形エリア枠を重ねる＋移動経路の境界通過を数える」。表示位置は自由な座標、移動の単位はエリアとして扱う。

これはAPIと既存コードに基づく技術判断であり、13.351実機でのドラッグ・描画・同期の実証はまだ行っていない。公式v13 API文書の表示バージョンは13.350であり、13.351との細部は実装前の技術検証で確認する。v14移行は前提にしない。

| 方式 | 評価 |
|---|---|
| 標準の正方形グリッドを巨大化 | 正方形の表示はできるが、通常スナップ・トークン寸法・標準距離計測が結びつく。長方形とエリア内自由移動には追加変更が必要 |
| 小さなグリッドを非表示にして大枠を重ねる | 配置が小マス単位になり、自由移動という要件には余分な制約が残る |
| **グリッドなし＋独自エリア枠** | **推奨**。トークン寸法とエリア寸法を独立させ、正方形・長方形に同じ処理を使える |
| エリアごとにRegionを作る | 任意形状やエリア効果には有用だが、規則的な矩形盤面には編集・データ管理が増える。今回の標準構成には使わない |

公式Scenes文書はグリッドなしと正方形グリッドを区別している。単位ラベルを「段階」に変えるだけでは、境界通過を数える計算にはならない。[Scenes](https://foundryvtt.com/article/scenes/)

## 2. 要件と設計上の提案

今回ユーザーから示された要件:

- 大きな正方形または長方形の1マスを1エリアとする。
- 同じエリア内なら、移動量にかかわらず段階移動は0。
- 隣のエリアへの移動は1段階。2エリア先への移動は2段階。
- わずかな距離でも境界を越えれば段階移動として扱う。
- 2026-09-12追加裁定: 斜め隣への移動は2段階、A→B→Aの往復も2段階。
- 同一エンゲージは至近、1つ隣は近、2つ隣は中、3つ隣は遠、4つ以上隣は超遠。「3つ隣以上が遠」と「4つ隣以上が超遠」は、4以上で超遠を優先する区分として整理する。

以下は技術設計の提案であり、未提供のゲームルールとして確定しない:

- 等間隔・軸に平行な矩形を行列状に敷く。幅と高さは別々に設定できる。大きさの異なるエリアの混在や多角形は今回の範囲外。
- 所属エリアは**トークンの中心点**で決める。画像の端がはみ出しても中心が越えるまでは移動扱いにしない。中心位置を小さく表示できるようにする。
- 確定した斜め2段階・往復2段階を、経路で通過した縦横の境界の加算で表現する。角を通って縦横の境界を同時に越える場合も2段階。単なるマウスの軌跡は経路に含めず、ドラッグの始点・終点と明示した経由点を使う。

```text
┌────────────────┬────────────────┬────────────────┐
│ A              │ B              │ C              │
│ ● → → ●  0段階 │                │                │
│             ● ─┼→ ●    1段階    │                │
│ ● ─────────────┼────────────────┼→ ●    2段階    │
└────────────────┴────────────────┴────────────────┘
```

## 3. ユーザー操作と表示

RLはSceneの「エリア戦闘」設定から、有効/無効、行数・列数、エリア幅・高さ、原点、線色・透明度を設定する。プレビュー上で枠の位置と寸法を調整できる。初回有効化の保存操作でグリッドなしへの変更内容を示す。既存Sceneは既定で無効。

例: トークンの基準寸法100pxに対し、エリア600×400px、5列×3行。幅・高さは実距離を意味せず、同一エリアに複数のトークンを並べるための表示寸法である。

プレイヤーは通常のトークンドラッグで移動する。所属エリアと通過経路をハイライトし、「エリア内移動」「1段階」「2段階」のようにプレビュー表示する。エリア内移動のたびにチャットを投稿しない。境界を越えた確定移動は履歴に残す。Escやドラッグ取消では何も消費しない。

通常の距離ルーラーとは別にTNXの段階を明示する。TokenRulerの拡張で表示を統合する候補があるが、標準の物理距離を段階数で全体上書きしない。照明・視界・壁・テンプレートは別の意味を持つためである。[TokenRuler](https://foundryvtt.com/api/v13/classes/foundry.canvas.placeables.tokens.TokenRuler.html)

## 4. 座標と段階計算

盤面はSceneのキャンバス座標で定義する。画面上のCSS座標、ズーム後の座標、背景画像の元ピクセルとは分ける。原点を含め、表示と判定で同じ値を使う。

```text
column = floor((centerX - originX) / areaWidth)
row    = floor((centerY - originY) / areaHeight)
areaId = row + ":" + column
```

中心点はTokenDocument.getCenterPoint相当の座標・寸法から得る。画像の透明余白・テクスチャ拡縮・回転は所属エリアに影響させない。[TokenDocument](https://foundryvtt.com/api/v13/classes/foundry.documents.TokenDocument.html#getCenterPoint)

経路を線分列として処理し、各線分と縦横の境界の交点で分割する。各区間と端点の所属セルを求め、連続する同一セルをまとめ、セル遷移ごとに段階を加算する。大きな1回のドラッグでも中間の境界を省略しない。表示フレームごとのサンプリングには依存しない。

確定した上下左右方式では、隣接する区間のセル差の `abs(Δcolumn) + abs(Δrow)` を加算する。同じ始点・終点だけの計算では折れ曲がりや往復を数えられないため、経路全体に適用する。移動コストと、2地点間の最短エリア距離は別の関数にする。

距離区分の設計は、2地点の `d = abs(columnB - columnA) + abs(rowB - rowA)` を用い、1＝近、2＝中、3＝遠、4以上＝超遠とする。同一エンゲージは至近。盤面上の同一エリアを同一エンゲージとして扱う対応を設計前提とする（今回の盤面に関する回答の文脈に基づく整理）。距離はトークン間のピクセル距離や過去の移動履歴に依存しない。

距離区分だけを4以上で超遠にまとめ、移動段階そのものは丸めない。例えば6エリア分を進む経路なら6段階を要する。A→B→Aは移動2段階でも、到着時のA内の相手との距離は至近となる。

境界上の点は左/上を含み、右/下を含まない半開区間で一意に割り当てる。外周の右端・下端は盤面外とする。交点付近の丸め誤差は座標を共通精度へ正規化して扱い、許容帯を無料で往来する仕様は設けない。境界で一度止めた移動と止めない移動の合計段階が一致することをテストする。

盤面外は所属エリアなし。エリア内移動0として誤認しない。表示段階では「盤面外／計測対象外」を返し、移動制限を有効にした段階では盤面外への経路を拒否する。RLの配置操作では盤面外配置を認める。盤面外→盤面内の初期配置は移動消費に含めない。

## 5. データの保存先

Actorに位置を保存しない。同じActorの複数トークンと複数Sceneを区別するため、位置の正本はTokenDocument、盤面定義の正本はSceneとする。

Sceneの新規フラグ案 `flags.tokyo-nova-axleration.areaCombat`:

```json
{
  "schemaVersion": 1,
  "enabled": true,
  "revision": 1,
  "origin": { "x": 200, "y": 200 },
  "cell": { "width": 600, "height": 400 },
  "rows": 3,
  "columns": 5,
  "style": { "color": "#88ccee", "alpha": 0.65 }
}
```

数値の有限性、幅/高さの正値、行列数の正整数、描画上限、Scene内の配置可能範囲を保存時に検証する。既存Sceneのフラグ欠落は無効として解釈し、一括書換えは不要。斜め方式と距離区分は確定ルールとして扱い、Sceneごとの切替設定は設けない。

所属areaIdは座標から導出し、永続化しない。描画キャッシュはScene ID＋revisionをキーに破棄できるものとする。移動中に盤面定義が変更された場合は古いプレビューを破棄して再計測する。

基本盤面の移動履歴表示はコアの移動履歴と直近の確定移動イベントから構成する。コア履歴を取得できない再読込後は「履歴なし」とし、現在位置だけから過去の移動を捏造しない。履歴は閲覧補助であり、消費残量の正本にはしない。独自の永続履歴や毎移動のチャット投稿は基本盤面に追加しない。

移動上限まで連携する段階では、Tokenの同一更新内に座標と移動記録を保存する案とする。記録にactionId、sourceMessageUuid、許可段階数、使用段階数、確定経路、盤面revisionを持たせる。Actor IDだけで記帳せずToken UUIDを使う。履歴保持期間はアクション/カット境界に限定してデータ肥大化を避ける。

## 6. FVTTへの接続

- `canvasReady`で枠を生成し、`updateScene`の設定変更で更新、Canvas破棄時に表示とリスナーを解放する。通常時の枠はクリックを遮らない描画にする。
- `preMoveToken`で確定経路を検査できる。更新要求を出すクライアントでのみ呼ばれ、falseで移動全体を拒否できる。経由点の変更はできない。非同期承認をこのフックの戻り値で待つ設計にはしない。[preMoveToken](https://foundryvtt.com/api/v13/functions/hookEvents.preMoveToken.html)
- `moveToken`は更新処理後に全接続クライアントで呼ばれる。表示更新に使えるが、「アニメーションが目的地まで完走した」と同義には扱わない。[moveToken](https://foundryvtt.com/api/v13/functions/hookEvents.moveToken.html)
- 移動データにはorigin、destination、passed、pending、id、chainがある。経路の進行・一時停止・継続を区別し、計画分を先に全部消費しない。アダプターで取得形を正規化し、同じ移動IDと処理済み区間を再計上しない。[TokenMovementData](https://foundryvtt.com/api/v13/interfaces/foundry.documents.types.TokenMovementData.html)
- 記帳・チャット生成は全クライアントで繰り返さない。activeGMの単一処理経路と既存の直列キューを使う。再接続やGM交代は永続記録から復元する。
- 幅・高さ変更、トークン初期作成、RLの配置修正、テレポート、強制移動は通常移動と区別する。座標の直接updateを含む各経路のフック発火を実機確認し、経路のない更新から架空の移動経路を推定して消費しない。

TokenRulerの拡張・CONFIG登録の正確な接続方法、コア経路の座標基準、途中停止時のpassed/pending更新順は技術検証の対象。公開API文書だけで全動作を保証せず、必要な拡張箇所をv13依存の小さなアダプターに閉じ込める。

## 8. 移動上限との連携設計

**今回の基本盤面は計測・表示を標準とし、上限超過を強制停止しない。** ユーザーの要件は境界通過を段階として扱うことであり、移動制限の自動強制までは要求されていない。以下の上限管理は追加連携案として分離し、基本盤面の実装をその承認待ちにしない。

既存のCombat_Flow.mdでは、ムーブの繰り返しをRLが止める運用が明示されている。また任意リアクションは締切操作を設けずライブに結果を導出する。そのため「1カット1回だけ」「妨害の受付を閉じるまで移動禁止」等は新設しない。基本盤面では手番外の配置も計測でき、ARやCSを変更しない。

上限管理を追加する場合の案:

1. 通常ムーブ・SF・移動判定結果から、その移動アクションの許可段階を取得する。
2. 同一アクションを複数回のドラッグに分けても消費を合算する。エリア内の配置調整は残量0でも可能。
3. 上限超過は確定前に止める。RL用の「配置変更」は明示的に分ける。
4. 対決移動や妨害は既存解決に接続し、判定成功表示だけでトークンを自動移動させない。「この結果で移動」は移動の開始操作であり、リアクション受付を閉じる操作ではない。操作時点のライブ結果を参照する。
5. 適用済み判定の事後修正では、既に起きた他の処理を無条件に巻き戻さない。差異を通知しRLが訂正する。二重適用をactionIdで防ぐ。

厳密な上限管理を採用する場合、クライアント側のpreMoveTokenだけでは同時操作の競合を防げない。移動要求をactiveGMへ集約し、Tokenごとに直列化し、最新位置・盤面revision・アクション残量・操作権を再検証する。座標と消費記録は同じToken更新にまとめ、成功後に結果通知する。失敗時に消費だけ残さない。重複要求IDを記録し、応答喪失後の再送にも同じ結果を返す。GM不在時は管理移動を保留して理由を表示する。

これは通常UIの競合対策であり、改変クライアントへのサーバー側強制とは異なる。移動計測だけの段階ではGM不在でも各クライアントで表示できる。

## 9. ルール上の未確定事項

| 論点 | 提案／実装前に確定する点 |
|---|---|
| 所属判定 | 中心点を推奨。画像の端を基準にするかは確認対象 |
| 移動枠の寿命（上限管理を追加する場合） | 移動ごとに開始・終了を明示する案。未消費段階を次の移動へ繰り越さない案の採否は未確定。基本盤面は枠を消費しないため影響なし |
| 強制移動・テレポート（上限管理を追加する場合） | 通常消費と区別する。基本盤面では通常移動と別表示にし、移動可能距離の裁定をしない |
| 同乗者の自動追従 | 同乗者も一緒に移動するルールは既存で確定済み。ただし乗車関係モデルを作らない裁定があり、現行データから対象を自動特定できない。基本盤面はRLの複数Token選択移動で扱い、自動追従は別途合意する |

この設計は上記を選択できる状態まで整理するもので、ユーザーのルール解釈を代行して確定するものではない。

### 基本盤面の設計判断

- 中心点で所属判定する。エリア内自由移動は残り移動量・手番状態・Actor種別では止めず、FVTTの既存操作権と壁の制約に従う。ゴーストにも独自の移動資格制限を追加しない。
- 距離表示は同じScene上の具体的な2つのTokenから求める。選択Tokenを起点に、ホバーまたはターゲットしたTokenとの距離区分を表示する。複数選択時に起点が一意でなければ距離表示を出さず、起点指定を促す。
- 同一エリアを1エンゲージとして表示する。エリア内の位置取りは見やすさのためのもので、命中・射程・至近判定を変化させない。
- 射程区分の表示は自動化するが、攻撃対象の自動除外や攻撃可否の強制は基本盤面に含めない。武器・技能の例外処理は既存の用途側に残す。
- 移動履歴は同じ操作をクライアントごとに投稿せず、非公開Tokenの経路は公開しない。基本盤面ではドラッグ中にDB更新を行わず、確定座標は通常のToken更新に任せる。

### 基本盤面の関数契約

追加する純計算は既存のFoundry非依存ルール層の規約に合わせる。

| 関数案 | 入出力と責務 |
|---|---|
| `validateAreaBoard(config)` | 正常/入力エラーを返す。描画上限は行列各100、積2500を初期案とし、実機負荷で調整する |
| `getAreaAtPoint(config, point)` | `{row, column}` または `null`。範囲外・非数は所属なし |
| `measureAreaPath(config, points)` | `{status, stages, transitions}`。statusはok/outside/invalid。範囲外経路のstagesはnullとし0扱いを防ぐ |
| `getAreaDistance(config, from, to)` | 対応する2地点間の縦横差の合計またはnull。経路の長さを参照しない |
| `getAreaRange(distance)` | 0/1/2/3/4以上を既存キーclose/short/middle/long/superLongへ対応。不正値はnull |

表示プレビューと確定計測で同じ純関数を使う。Scene/Tokenを純関数へ渡さず、FVTT接続側で中心座標と設定値に変換する。停止・継続時は進行済みの経路を正規化してから呼ぶ。

### 既存移動情報の参照表

| 移動の種類 | 参照値 | 連携時の扱い |
|---|---|---|
| 生身の通常ムーブ | 1段階 | 判定は新規に要求しない |
| ヴィークルの通常ムーブ | 準備済みvehicleの実効`speedFactor` | mode=valueの有効数値を読む。noneを勝手に1へ置換しない。解決不能なら「移動上限不明」と表示 |
| 操縦判定によるメジャー移動 | 既存`movementStagesFromAchievement` | SFとの加算はしない。ファンブル/スート不一致/移動失敗は既存結果に従い0 |
| 対決あり移動 | 対決カードの現在の成否と移動段階 | 複数の任意リアクションを尊重し、後続の妨害による失敗へ追随 |
| 離脱 | 既存の離脱用途の成否 | 離脱の成功だけから移動段階数を生成しない |

後から結果が覆った場合は表示上の段階情報を更新し、位置の訂正が必要なことをRLに示す。以前の位置への自動復帰は行わない。既に別の移動や攻撃が行われている可能性があり、位置だけを戻すと状態が食い違うためである。

## 10. 実装の分割と受入条件

追加ファイルの基本案は、純計算 `scripts/rules/area-combat.mjs`、FVTT接続・描画 `scripts/combat/area-combat.mjs`、設定画面 `scripts/app/tnx-area-combat-config.mjs` と対応テンプレート。描画処理が大きくなる場合だけ分割する。起動登録は既存coreの担当箇所に追加し、機能専用の大量の小ファイルは作らない。

| 作業単位 | 完了条件 |
|---|---|
| 技術検証 | 13.351で自由ドラッグ、ルーラー拡張、中心座標、経由点、途中停止、直接update、複数PL同期を確認 |
| 盤面設定・描画 | 正方形/長方形、ズーム/パン、再読込、Scene切替、サブシーン背景差替えで枠が一致し、既存Sceneは無効のまま |
| 段階計測・表示 | 以下の純計算と実機操作の受入例を満たす。実経路とプレビューに差がある場合は確定経路の値を表示 |
| 移動情報の表示連携 | 通常/SF/判定/対決の各参照経路と結果の事後変更を検証。移動上限の強制は追加連携として別途採否を決める |

実装の完了単位は「設定・枠描画」「境界計測・距離表示」「既存移動情報の表示連携」の3つ。これらで今回の自由配置と段階移動の要件を満たす。上限の強制、永続する移動枠、同乗者の自動特定と追従、射程外攻撃の自動拒否は基本盤面の完了条件に含めない。

純計算の受入例（確定した斜め・往復・距離区分を含む）:

- 同一エリア内を大きく移動して0。境界の手前から向こうへ数px移動して1。
- 2境界を1回のドラッグで越えて2。A→B→Aの明示経由で2。
- 斜めに縦横1本ずつ越えて2。角を正確に通っても2。
- 距離区分は同一エンゲージ＝至近、エリア差1＝近、2＝中、3＝遠、4/5/6＝超遠。斜め隣は差2で中。
- 6エリア分の移動は距離区分が超遠でも6段階。往復の移動コスト2と、到着時の距離0を混同しない。
- 境界上で分割/未分割の合計が一致。境界に沿った移動で横方向の架空の消費がない。
- 長方形・非ゼロ原点・大きなトークン・テクスチャ拡縮でも中心基準で一致。
- 外周外の経路は計測対象外になり、無料移動として扱われない。

実機の受入例:

- マウス、キーボード、経由点、複数Token同時移動、途中停止/継続、取消/Undoを確認。
- 壁で短縮された実経路を計測。壁や視界に関する既存FVTTの制約を無料移動が無効化しない。
- 隠されたトークンの位置・移動履歴を権限のないプレイヤーへ表示しない。
- 登場での配置と移動を混同しない。複数Tokenを持つ同一Actorでも位置が混ざらない。
- 無効Sceneでは標準ルーラー・配置・既存戦闘進行に回帰がない。

新規純計算は意味のある境界例でテストし、接続処理は既存のテスト構成に合わせる。実装時に関連テストとlintを行い、描画・ドラッグ・同期は実機で補う。今回はドキュメントだけなので実装テストは実行していない。
