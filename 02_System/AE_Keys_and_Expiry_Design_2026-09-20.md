# 付与AE・キー再設計・判定1回持続（2026-09-20）

状態: ユーザー追加指示の記録と設計案。コード変更なし。基本移行計画への追補。

## 確定した追加要件

- 通常AEと付与AEの混在効果は存在しない。分割機能は不要。
- 付与AEは「アウトフィットへの付与」を行う。技能・神業等のItemは付与対象に含めない。
- 付与AEに「このアイテム自身に適用」を追加。保存名の候補は既存applyToParentと対になる `flags.tokyo-nova-axleration.applyToSelf`。
- 「準備先に適用」「このアイテム自身に適用」はチェックボックスで表示する。ラジオボタンにはしない。
- 両チェックは「効果を対象に適用」の状態にかかわらず表示する。
- 通常AEから「準備先に適用」を除去する。付与AEからステータス状態関連機能を除去する。表示だけでなく入力・保存・付与マーカー・状態反映まで対象。
- 自分自身にも準備先にも適用しない付与AEは、用途実行時のチャットカードにドロップエリアを出し、対象アウトフィットをドロップして付与する。
- 効果時間に「次の1回の判定まで」を追加する。
- 適用先チェックは排他。自動適用オン時は必ず一方のみtrue、オフ時は両方falseも許可し、その場合はチャットドロップ付与。両方trueは禁止。
- 「次の1回の判定まで」は効果条件に一致する判定の確定後に消費する。中止では消費しない。
- 式のキーとAE属性キーを、最新版D&D 5eを参考にわかりやすく再設計する。

## 確認待ち

1. 適用先チェックの条件と排他選択は確定済み。自動適用オンへの切替時に両方オフなら、適用先選択を求める案（暗黙の対象変更を避ける）。
2. 判定確定後の消費は確定済み。複数対象への判定・判定後のダメージ処理をどこまで同一判定として扱うかは詳細設計対象。
3. 付与AEの判定1回持続を、持ち主の条件に一致する判定で消費するか、そのアウトフィットを使用した条件一致判定で消費するか。判定をせずシーン／アクトが終了した場合の失効条件。
4. ドロップ付与は用途1回につきアウトフィット何個か。所持品以外のワールド／パックの原本を対象にするか。提案は所持アウトフィットの実体を対象とし、権限を検証、他者所有は既存のGM処理経路を使う。個数・対象範囲はユーザー確定を待つ。

## D&D参照と採用方針

2026-09-20に公式latestが **6.0.3** を指すことを確認。ローカル導入版は6.0.2なので、最新仕様の根拠と混同しない。

- [6.0.3 release](https://github.com/foundryvtt/dnd5e/releases/tag/release-6.0.3)
- [Roll Formulas](https://github.com/foundryvtt/dnd5e/wiki/Roll-Formulas): 式で `@abilities.str.value`、`@item.uses.max` 等の文脈別の参照を公開。
- [Active Effect Guide](https://github.com/foundryvtt/dnd5e/wiki/Active-Effect-Guide): AE属性に `system.abilities.*`、`system.rolls.ability.check.bonus` 等を使用。
- [Enchantment](https://github.com/foundryvtt/dnd5e/wiki/Enchantment): アイテム側の属性変更の参考。

以下はD&D仕様そのものではなくTNX向けの提案。能力値の3文字略称などはそのまま輸入せず、reason等の既存語彙を維持。チャットドロップの仕様はユーザー指示に基づき、D&Dと細部まで一致するとは仮定しない。

## キー設計案

### 式: 読む値

| 意味 | 現行例 | 新キー案 |
|---|---|---|
| 理性の実効能力値 | `@system.reason.total` | `@abilities.reason.value` |
| 理性の実効制御値 | `@system.reason.totalControl` | `@abilities.reason.control` |
| 保持元アイテムの実効技能レベル | `@item.self.system.levelTotal` | `@item.level` |
| 識別キーで指定した技能の実効レベル | `@item.eika.system.levelTotal` | `@skills.eika.level` |
| 効果保持先アウトフィットの実効攻撃力 | `@item.self.system.attack.total` | `@item.attack.value` |
| 準備先の実効攻撃力 | `@item.parent.system.attack.total` | `@parent.attack.value` |
| 指定アウトフィットの実効攻撃力 | `@item.weaponKey.system.attack.total` | `@outfits.weaponKey.attack.value` |
| 対象キャラクターの能力値 | `@target.system.life.total` | `@target.abilities.life.value` |
| 判定結果 | `@achievement` / `@diff` / `@card` | `@check.achievement` / `@check.margin` / `@check.card` |

`@item` は現在の保持先（用途なら用途を持つItem）、`@parent` はその準備先に固定し、付与後に元定義を指すよう意味を変えない。付与元を参照する必要がある場合は別の `@source` 文脈として明示設計する。`@target` をアウトフィット付与先の意味に使い回さない。

`value` は公開する実効値、素値が必要な属性は `base` を明示する案。ただし使用回数の最大値など既存の評価タイミングは保持し、キーの短縮でAE適用前／後を変えない。旧value参照を無条件に新valueへ置換しない。

### AE属性: 変更する値

| 意味 | 現行例 | 新キー案 |
|---|---|---|
| 理性の能力値補正 | `system.ability.reason` | `system.abilities.reason.value` |
| 理性の制御値補正 | `system.control.reason` | `system.abilities.reason.control` |
| 全判定の補正 | `check.all` | `system.rolls.check.bonus` |
| アウトフィットの攻撃力 | `system.attack.value` | `system.attack.value`（維持） |
| 技能レベル補正 | `item.eika.system.level` | `system.skills.eika.level` |

公開語彙を揃えるが、「式で読める値はすべて変更可能」とはしない。変更可能な属性・型・許可モード・適用時期を属性定義として管理する。
AE属性は保存データを無条件に直接変更するパスではなく、TNXの実効値適用先へ解決する。Foundry標準適用による二重適用を引き続き抑止する。
付与対象の選択はチェック／用途／ドロップが担い、属性キーへ準備先・自分自身の意味を重ねない。旧カテゴリ・識別キーによる付与先指定は、既存挙動を失わない対応表を別途作る。

### わかりやすさと互換移行

- 「理性 → 能力値」「アウトフィット → 攻撃力」等の日本語候補と内部キーを一緒に表示する。式にも参照候補と意味・利用可能な文脈を示す。
- 全キーの旧→新対応表に、値の意味・適用先・型・評価タイミングを記載する。
- 新旧両方を解決できる読込層を先に実装し、新規保存は新形式へ統一する。既存式はトークン単位で変換し、文字列の一括置換は使わない。
- 技能／アウトフィット以外の既存Item参照、識別キーの数字・ハイフン・予約語衝突、条件・ワイルドカードを棚卸しする。対応先が確定しない参照は旧形式で保持する。
- 判定、ダメージ、AE、使用回数、用途、プリセット、チャットの保存式を同じ対応表で検証する。
- 内部DataModelの全面改名と公開キー整理は別工程にする。最初は変換層で公開キーを整え、派生計算を壊さない。

## ドロップ付与の設計作業

用途実行→チャットカードの付与待ち領域→アウトフィットのドロップ→対象実体・条件・権限確認→付与→カード表示更新という流れを設計する。
技能・神業など非アウトフィットは対象外。付与定義と付与インスタンスを分け、チャットの再描画・同時ドロップ・再操作で意図せず重複付与／用途再消費しないよう処理済み情報を保持する。
対象数・再付与可否・キャンセル時の用途消費の扱いは、既存の用途規則との対応を確定してから実装する。

## 「次の1回の判定まで」の設計作業

- 保存値候補 `nextCheck`。時間の長短を表す既存のDURATION_RANKには混ぜず、判定イベントによる失効条件として扱う。
- 条件に合う判定の開始時に、その判定へ適用する効果を特定する。判定中に新規付与された効果を同じ判定で即消費しない。
- 失効時点は条件一致判定の確定後（ユーザー確定）。中止では消費しない。プレビュー・再描画で消費せず、判定IDで重複消費を防ぎ、再読込後も処理済み判定を区別する設計とする。
- 攻撃判定後のダメージに必要な値は判定時の文脈に保持する案。効果の削除で同一行動のダメージ結果が変わらないよう、どこまでを1回とするか確定する。
- 自動転送コピーを単に削除すると供給元から再生成される可能性があるため、消費単位（供給元／付与インスタンス）と再生成抑止を設計する。
- 新規選択肢・表示だけでなく、Actorとアウトフィットの両方について失効・持続表示・再付与・同時処理を試験する。

## 実施順序

適用先チェックの整合条件と判定消費条件を確定→新旧キー対応表と型別仕様表→V14保存形式修正→付与AEの適用処理／ステータス分離→チェックUIとチャットドロップ→判定1回持続→複製ワールドで移行・復元検証。
キーの読込互換層は早期に用意するが、保存式の一括変換は型・適用先の仕様が固まってから行う。
